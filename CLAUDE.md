## Правило: изменения index.html

Любой запрос на изменение **структуры или визуала сайта** (`index.html`) — новые блоки, вкладки, дизайн, компоненты — требует предварительного чтения алгоритма сборки:

→ [docs/spec-pilot.md](docs/spec-pilot.md)

**Когда читать:** запрос содержит «добавь», «сделай», «перенеси», «измени» применительно к `index.html` или к тому как сайт выглядит или работает.

**Когда не читать:** правка сигналов (`signals.json`, `SIGNALS.md`), обновление документации, мелкие однострочные правки с очевидным решением.

**Исключение — новый кластер.** Создание нового `cluster` (Шаг 4) требует точечных записей в **трёх** отдельных lookup-таблицах внутри `js/app-main.js` (JS вынесен из index.html, см. ниже) — `DIGEST_CLUSTER_LABELS` (короткие подписи, фильтры вкладки Сигналы), `CLUSTER_LABELS` (длинные подписи, карточки «Главные нарративы», отдельная функция) и `CLUSTER_LABELS_AI` (AI-анализатор, `localAnalyzeSignal()`) — иначе в соответствующем месте сайта вместо человеческой подписи покажется сырой `SNAKE_CASE`. **Было «двумя» до 2026-07-27** — при реальном разделении кластера (пилот `quantum_security`) обнаружено, что третья таблица существовала, но не была здесь задокументирована. Это точечная запись во все три lookup-таблицы (`new_cluster_key: 'ЭМОДЗИ ПОДПИСЬ'`), не структурное и не визуальное изменение — `spec-pilot.md` для неё не читать. Всё остальное в `js/app-main.js`/`index.html` по-прежнему не трогать при работе с сигналами.

## Сигнал: схема объекта

Каждый новый сигнал записывается в `signals.json`. `SIGNALS.md` — производная проекция: **не редактируется руками** — после записи сигнала (или правки существующего) запускается `python3 scripts/build_signals_md.py`, результат коммитится тем же PR. Тест-страж `tests/unit/test_signals_md_sync.py` проверяет байт-в-байт синхронность на каждом прогоне — ручная правка `SIGNALS.md` в обход генератора будет откачена ближайшим запуском скрипта и не пройдёт CI.

> **История правила (2026-07-19):** до этой даты действовало «два файла одновременно» — оба редактировались руками параллельно. Без механизма проверки за несколько месяцев это разошлось: порядок блоков перестал соответствовать заявленной сортировке (`date` DESC), часть текстовых полей в `.md` отстала от более новых правок в `.json`. Тот же класс проблемы, что уже был решён для FACTS (AD-6) и SITE_MAP — процедура без механизма не держится.

```json
{
  "id": "STR-2026-0623-001",
  "date": "YYYY-MM-DD",
  "cat": "ownership",
  "catLabel": "🏛️ ВЛАДЕНИЕ",
  "dir": "neg",
  "horizon": "mid",
  "theme": "institutionalization",
  "weight": "media",
  "actor": "corporate",
  "flow": "outflow",
  "signal": "Заголовок сигнала",
  "data": ["метрика 1", "метрика 2"],
  "context": "Исторический контекст и аналогии.",
  "caveat": "Риски и ограничения интерпретации.",
  "alternatives_considered": [
    "Отклонённая интерпретация — почему отклонена"
  ],
  "alternative_scenario": "Опционально, если уверенность не высокая: связный альтернативный путь развития, если основная интерпретация неверна",
  "facts": [
    { "key": "entity_id.metric", "value": 123456, "unit": "BTC", "as_of": "YYYY-MM-DD" }
  ],
  "source": "Источник (месяц год)",
  "links": {
    "confirms": ["id сигнала который этот усиливает"],
    "contradicts": ["id сигнала с которым в противоречии"],
    "context_chain": ["id сигнала из контекста которого вырастает этот"]
  },
  "narrative_role": "complication",
  "cluster": "strategy_model_stress",
  "tension": "краткое описание противоречия которое сигнал раскрывает",
  "macro_implication": "что означает на уровне общей картины",
  "preset_question": "Опционально — короткий вопрос для кнопок AI-анализатора, см. правило ниже"
}
```

- Все три поля `links` — массивы **id** (не заголовков)
- `index.html` для сигналов не трогать — данные загружаются из `signals.json` через fetch

## Справочник значений полей

> Формат и допустимые значения — здесь. Доменный смысл значений (связь с онтологией) → [docs/DATA_DICTIONARY.md](docs/DATA_DICTIONARY.md). Те же формулировки смысла — machine-readable, в `schemas/signal/v1.json` (`oneOf` с `description` на каждое значение вместо голого `enum`); синхронность с таблицами ниже проверяется тестом `tests/unit/test_claude_md_schema_sync.py`.

**`id`** — формат `PREFIX-YYYY-MMDD-NNN`. Префикс выбирается по `theme` **на момент создания**:

| Префикс | theme | Смысл темы |
|---------|-------|-----------|
| `SUP` | `supply` | Дефицит, эмиссия, потерянные монеты |
| `STR` | `institutionalization` | ETF, корпорации, правительства, владение |
| `INF` | `infrastructure` | Lightning, Layer 2, майнинг |
| `MAC` | `macro` | Ставки, ликвидность, макро-давление |
| `NAR` | `narrative` | Философия, регуляция, нарративы |

**Правило неизменности `id`:** после записи `id` не меняется никогда — на него ссылаются `links` других сигналов. Если `theme` сигнала уточнилась позже, префикс остаётся историческим; расхождение префикса и темы задним числом не исправляется.

**`dir`** — что сигнал говорит о силе Bitcoin как актива в своём горизонте:

| Значение | Смысл |
|----------|-------|
| `pos` | усиливает позицию BTC |
| `neg` | создаёт давление на BTC |
| `neu` | структурный факт без направления |

**`horizon`** — временной горизонт:

| Значение | Смысл |
|----------|-------|
| `short` | недели–месяцы |
| `mid` | месяцы–год |
| `long` | годы, структурные изменения |

**`weight`** — достоверность источника:

| Значение | Смысл |
|----------|-------|
| `onchain` | верифицируемые данные блокчейна |
| `market` | биржевые данные, цена, объёмы |
| `media` | медиа, аналитики, оценки |
| `primary` | первичный источник (высказывание, документ) |

**`actor`** — субъект сигнала:

| Значение | Смысл |
|----------|-------|
| `etf` | биржевые фонды (BlackRock, Fidelity) |
| `corporate` | публичные компании (Strategy, MSTR) |
| `government` | государственные резервы |
| `defi` | протоколы, on-chain структуры |
| `retail` | розничные инвесторы |
| `miner` | майнеры |

**`flow`** — направление капитала:

| Значение | Смысл |
|----------|-------|
| `inflow` | капитал входит в BTC |
| `outflow` | капитал уходит из BTC |
| `internal` | перераспределение внутри структуры |
| `neutral` | движения капитала нет или неизвестно |

**`cat` / `catLabel`** — категория и её отображаемая метка. `catLabel` выводится из `cat` строго по таблице — никаких вариаций регистра, эмодзи или синонимов:

| cat | catLabel (канон) | Примеры |
|-----|------------------|---------|
| `onchain` | 📊 ON-CHAIN | Production Cost, MVRV, NVT |
| `macro` | 🏦 МАКРО | Ставки, ликвидность, DXY |
| `mining` | ⛏️ МАЙНИНГ | Хешрейт, сложность, капитуляция |
| `narrative` | 📰 НАРРАТИВ | Регуляция, институционалы, события |
| `layer2` | 🔗 LAYER 2 | Stacks, Lightning, сайдчейны |
| `ownership` | 🏛️ ВЛАДЕНИЕ | Распределение по типам владельцев |

> **Факт о рендере (2026-07-03):** в текущем `index.html` `catLabel` используется в разметке только как fallback, который не срабатывает — реальную подпись на карточке даёт `DIGEST_CLUSTER_LABELS[cluster]` (см. «Кластеры» ниже). `catLabel` тем не менее остаётся обязательным и канонизированным полем данных: это дата-контракт для будущих потребителей `signals.json` (не только текущий index.html), а чеклист Шага 8 по-прежнему требует его сверки с `cat`.

> Категория `ta` (технический анализ) депрецирована в v6.0: технический анализ выведен за границы предметной области (обоснование → [docs/BDKS.md](docs/BDKS.md), Раздел 1). Исторических сигналов с этой категорией нет; новые не создаются.

| `lightning_payments` | Компромисс скорость/доверие в around-Bitcoin расчётных системах — Lightning, некастодиальные кошельки, 0-conf |
| `wallet_security_incidents` | Криптографические/реализационные провалы в инструментах self-custody (аппаратные кошельки, генерация ключей) — отдельно от quantum_security (там угроза будущая и протокольная, здесь — сегодняшняя и в реализации конкретного вендора) |
| `btc_payment_adoption` | Реальное использование BTC для платежей/переводов на уровне стран и пользователей — разрыв между политическими декларациями (legal tender) и фактическим поведением людей |

> **План завершён (2026-07-27):** `btc_infrastructure_growth` (30% базы, 5 содержательно разных подтем) полностью разделён на 5 новых кластеров — `quantum_security`, `mining_operations`, `layer2_programmability`, `mining_ai_diversification`, `lightning_payments`. Исходный кластер упразднён полностью (0 сигналов после последнего переноса) — удалён из `ontology.json` и обоих словарей подписей. `NAR-2026-0626-001` (Kalshi) отдельно переклассифицирован в `etf_institutional_flow`. Полная история решений → [archive/PLAN-infrastructure-cluster-split.md](archive/PLAN-infrastructure-cluster-split.md) (закрыто, см. архив).

> **Исключение из правила «2+ сигнала» (2026-07-30):** `wallet_security_incidents` создан на одном сигнале (`INF-2026-0730-001`, RNG-баг Coldcard) — обоснованное отступление, не прецедент по умолчанию. Причина: ни один существующий кластер не подошёл ни по теме, ни по субъекту (ближайший — `quantum_security`, но там угроза принципиально другая — будущая и протокольная, не сегодняшняя реализационная), а прежний catch-all `btc_infrastructure_growth` к этому моменту уже полностью упразднён — оставлять `cluster` без валидной ссылки на `ontology.json` означало бы либо сломать референциальную целостность (поймал бы `validate_integrity.py`), либо мисклассифицировать сигнал. Создавать новый кластер на одном сигнале — по-прежнему НЕ норма; здесь решение приняли осознанно, при отсутствии лучшей альтернативы.

> **Второе исключение (2026-07-31):** `btc_payment_adoption` создан аналогично, на одном сигнале (данные Центробанка Сальвадора — доля BTC-переводов 0,7% спустя 5 лет статуса legal tender). Ближайший по сущности кластер (`btc_treasury_competition`, там уже 2 сигнала о резерве Сальвадора) не подошёл по субъекту — резерв как накопление vs BTC как реально используемое платёжное средство — разные вопросы. Та же логика: не подгонять под существующий ради избежания нового кластера.

- Актуальное число сигналов кластера считается по `signals.json` — в этом файле счётчики не ведутся
- Новый кластер создаётся когда появляется 2+ сигнала с общим `tension` которого нет в существующих
- Создание кластера = **пять мест одновременно** (не два, не четыре — история находок: 2026-07-07 при создании `leverage_deleveraging_cycle` нашли расхождение 2→4; 2026-07-27 при пилоте `quantum_security` (разделение `btc_infrastructure_growth`) нашли ещё одно, 4→5):
  1. `cluster` в новом сигнале (`signals.json`)
  2. `ontology.json` → `clusters` — фактический источник истины, на который явно ссылается описание поля `cluster` в `schemas/signal/v1.json` («должен существовать в ontology.clusters»); не проверяется тестами автоматически, но обязателен для непротиворечивости
  3. `DIGEST_CLUSTER_LABELS` (`js/app-main.js`, короткие подписи для фильтров вкладки Сигналы)
  4. `CLUSTER_LABELS` (`js/app-main.js`, отдельный словарь — длинные подписи для карточек «Главные нарративы»)
  5. `CLUSTER_LABELS_AI` (`js/app-main.js`, словарь AI-анализатора — `localAnalyzeSignal()`; существовал с 2026-07-25 (Вариант C, бессерверный анализатор), но не был здесь задокументирован до 2026-07-27)

  Пропуск любого из 2–5 — кластер существует в данных, но на сайте (или в ответе AI-анализатора) отображается некрасиво (сырой `SNAKE_CASE`) в соответствующем месте. Для этой правки (все пять — lookup-таблицы/источник истины, не структура/визуал) `spec-pilot.md` по-прежнему не читать, см. «Правило: изменения index.html» выше.

## Алгоритм обработки сигнала

**Правило видимости рассуждения:**
Шаги 3 (Разбор), 4 (Кластеризация), 5 (Связывание) и 6 (Синтез) содержат интерпретационные решения, не механические проверки: выбор `narrative_role`, формулировка `tension`/`macro_implication`, состав `confirms`/`contradicts`/`context_chain`, причина выбора `cluster`. Эти решения и их обоснование показываются пользователю в чате до сборки итогового JSON — отдельным разбором по шагам, а не только результатом.

«Сводка после записи сигнала» (см. ниже) — краткое резюме уже показанных и принятых решений, а не единственное место, где они становятся видны. Свернуть весь процесс сразу в эту сводку недопустимо, даже если шаблон сводки кажется самодостаточным.

```
✗ Claude молча проходит Шаги 3–6 внутри себя, показывает только готовый JSON + сводку
✓ Claude показывает разбор (что это / контекст / что значит / оговорки), затем
   обоснование cluster и links, и только потом — оформление и сводку
```

### Шаг 1 — Приём материала

Определить формат входящего материала: текст, ссылка, скриншот.
Зафиксировать что именно прислал пользователь — это исходная точка, не интерпретация.

**Ограничение:** Claude не наполняет сигналы из собственных знаний. Только из материала пользователя. Переход к следующему сигналу — только после явного подтверждения пользователя.

### Шаг 2 — Исследование

Найти первоисточник:
- Если дана ссылка → `fetch` по ней
- Если нет → `web_search` по ключевым фактам материала

Найти 2–3 дополнительных источника по типу сигнала:

| Тип сигнала | Источники |
|------------|-----------|
| Корпоративные покупки BTC | Arkham, SEC filing, пресс-релиз |
| ETF / регуляторика | SEC.gov, Bloomberg ETF, проспект |
| Майнинг / инфраструктура | Hashrate Index, Glassnode, отчёты |
| Макро / on-chain | Glassnode, CryptoQuant, VanEck ChainCheck |
| Нарративы / медиа | Bitcoin Magazine, CoinDesk, The Block |

- Если источники противоречат — зафиксировать расхождение, оно войдёт в `caveat`
- Если первоисточник недоступен — сообщить пользователю и работать с тем что есть

### Шаг 3 — Разбор

Структурировать собранный материал по четырём пунктам:

- **Что это** — краткое определение события или факта
- **Контекст** — исторические аналогии, предыдущие прецеденты
- **Что означает сейчас** — интерпретация для BTC
- **Важные оговорки** — риски, ограничения, противоречия источников

Внутри пункта «Что означает сейчас» — рассмотреть минимум одну содержательную альтернативную интерпретацию и явно её отклонить с причиной (не соломенное чучело — альтернатива должна объяснять те же факты иначе). Отклонённые альтернативы фиксируются в `alternatives_considered`, не только проговариваются в чате.

Если уверенность в выбранной интерпретации не высокая (качественная оценка — источник не первичный, факты неполные, есть заметное расхождение источников) — сформулировать `alternative_scenario`: связный путь развития, которым может пойти ситуация, если основная интерпретация неверна, не просто «а вдруг наоборот» (ADR-015). Поле опционально — не заполнять, если уверенность высокая.

Это читаемый промежуточный артефакт. Из него питаются поля JSON:

| Пункт разбора | Поля JSON |
|--------------|-----------|
| Что это | `signal`, `cat`, `catLabel`, `actor`, `flow` |
| Контекст | `context` |
| Что означает сейчас | `dir`, `horizon`, `weight`, `theme`, `alternatives_considered`, `alternative_scenario` |
| Важные оговорки | `caveat`, `data` |

Поля `id`, `date`, `source` заполняются отдельно: `source` — название источника и месяц, `id` — на шаге 8.

**Правило определения `date`:**
`date` — дата события, берётся из самого проверенного источника, найденного на Шаге 2, а не выводится расчётом от относительных формулировок пользователя («вчера», «сегодня», «на этой неделе») и не от даты сессии.

Приоритет источника даты:
1. Дата/период в самом первоисточнике (официальный релиз, regulatory filing, документ) — высший приоритет
2. Дата публикации наиболее авторитетного вторичного источника (Шаг 2, колонка «Источники»)
3. Если ни один источник дату не называет явно — спросить пользователя напрямую, не предполагать

```
✗ Пользователь: «отчиталась вчера» → Claude молча вычисляет: сегодня минус 1 день
✓ Claude берёт дату из самого filing/источника; если расходится с «вчера» пользователя —
   фиксирует это расхождение и уточняет, а не выбирает дату самостоятельно
```

Если источники расходятся в дате — расхождение идёт в `caveat`, используется дата самого первичного источника.

### Шаг 4 — Кластеризация

Определить `theme` по справочнику полей.

Определить `cluster` по двум признакам одновременно:
1. `theme` совпадает с темой кластера
2. Субъект события (`actor` + суть действия) совпадает с описанием кластера

Если оба признака совпадают → кластер найден.
Если только `theme` совпадает → потенциально новый кластер (создаётся при 2+ сигналах с общим противоречием которого нет в существующих).

Кластер назначается здесь. `tension` формулируется только на шаге 6 — не использовать его как критерий поиска на этом шаге.

### Шаг 5 — Связывание

Найти кандидатов: все сигналы с тем же `theme`. Если кластер определён — добавить все сигналы того же кластера.

**Обязательный дополнительный шаг (с 2026-07-25, ADR-018):** прогнать `python3 scripts/find_similar_signals.py <ID нового сигнала>` — расширяет пул кандидатов за пределы одного `theme`/`cluster`, куда обычный поиск кандидатов выше не смотрит. Метод — TF-IDF (уни+биграммы) + пересечение по сущностям (`ENTITIES.json`) + флаг противоположного `dir` при том же `theme`. **Это только генерация кандидатов, не решение** — каждый кандидат из вывода скрипта проверяется теми же тремя честными тестами ниже, что и кандидаты из `theme`/`cluster`. Высокий скор или флаг `★ ОБЩАЯ СУЩНОСТЬ`/`⚡ ПРОТИВОПОЛОЖНЫЙ dir` — повод проверить в первую очередь, не готовый ответ. См. `docs/ADR-018-signal-similarity-candidate-expansion.md` — там же зафиксировано, почему сравнение по одним категориальным полям (`theme`/`actor`/`dir`) без текста — плохая замена: на 92 сигналах всего 32 уникальные комбинации (theme, actor, dir), слишком грубо для ранжирования.

**То же самое касается `suggest_contradictions()`/`semantic_inverse_score()`** (`scripts/contradiction_detector.py`) — известная, измеренная precision ~54–66% в зависимости от датасета (см. `docs/PLAN-open-initiatives.md` Часть 2 для актуального статуса и плана, `docs/ADR-012-contradiction-precision-target.md` для истории порога). Это не повод игнорировать инструмент — это причина никогда не пропускать три честных теста ниже даже для high-score кандидата.

Для каждого кандидата (из обоих источников) проверить три критерия:

**`confirms`** — оба сигнала говорят одно и то же но через разные механизмы?
→ Если да: добавить в `confirms`

**`contradicts`** — `macro_implication` двух сигналов описывают **несовместимые состояния одной системы**?
Тест: можно ли одновременно быть правым и в A, и в B?
→ Нет → добавить в `contradicts`
→ Да → не добавлять

**Запрещено** добавлять `contradicts` чтобы сделать сигнал победителем tension кластера. Чтобы сменить tension кластера — добавить **новый** сигнал с более сильным `tension` (см. «Нарративный синтез»); `tension` уже записанного и учтённого в синтезе сигнала не редактируется задним числом (Immutability Policy, `docs/NIES.md` AD-7, закрыт в пользу D13 — 2026-07-05).

**`context_chain`** — без понимания сигнала X текущий сигнал теряет смысл?
→ Если да: добавить в `context_chain`

Пустое поле — норма если после проверки всех кандидатов критерий не выполнен ни разу (в т.ч. если скрипт из Фазы 1 не нашёл ни одного кандидата, прошедшего честный тест — это тоже валидный, ожидаемый результат, не повод считать шаг невыполненным).
Не добавлять связь только потому что сигналы близки по теме.

### Шаг 6 — Синтез

Выполняется только после завершения шага 5.

**`tension`** — противоречие между двумя силами, не описание факта:
- Формула: «X vs Y» / «X несмотря на Y» / «X при условии что Y»
- Два конкретных механизма в столкновении, минимум 3 значимых слова по каждую сторону — не сводить конфликт к одной стороне-описанию
- Длина — **~150–220 символов** (жёсткий диапазон проверки — 40–250, см. `tests/golden/test_tension_benchmarks.py`; поднят с 220 до 250 по решению пользователя 2026-07-27 — но целиться в середину диапазона, не в край)
- **Самостоятельный** — описывает конфликт ТЕКУЩЕГО сигнала целиком сам по себе, без отсылок к другим сигналам («как в предыдущем сигнале», «как предсказывалось» и т.п.). Найдено пользователем на реальном примере (2026-07-27, `INF-2026-0722-001`): `context_chain` корректно указывал ID, но сам tension ссылался на «предыдущий сигнал» безымянно — на карточке tension показывается как самостоятельный заголовок (золотая полоса), читатель не видит рядом ID из `context_chain`, отсылка повисает без антецедента. Если нужен контекст другого сигнала — это работа `context`/`macro_implication`/`context_chain`, не `tension`. Проверяется механически (не только на словах) — `scripts/check_new_tension.py` ловит список типичных безымянных фраз
- Всегда начинается с заглавной буквы

| ❌ Плохо | ✅ Хорошо |
|---------|---------|
| «Strategy продолжает покупать BTC» (нет противоречия) | «Strategy наращивает долг для покупки BTC vs рынок ставит NAV-дисконт 0.83x» |
| «ETF показал отток» | «ETF-оттоки как поверхностное давление vs долгосрочные держатели покупают в 10x больше» |
| «...— именно то, что предсказывалось как риск в предыдущем сигнале» (безымянная отсылка, не самостоятелен) | «Майнеры диверсифицируются в AI как стратегию выживания vs продолжают продавать BTC-резервы для финансирования этой же диверсификации» (конфликт понятен без внешних отсылок; связь с предыдущим сигналом — в `context_chain` и `context`) |

**`preset_question`** (опционально, 2026-07-28) — короткий готовый вопрос для кнопок AI-анализатора («ИЛИ ВЫБЕРИ ИЗ БАЗЫ», вкладка SIGNALS). Дополняет курируемый пул из 4 вопросов на кластер (`CLUSTER_PRESET_QUESTIONS` в `js/app-main.js`) — не заменяет его, расширяет разнообразие конкретикой момента.

- Пишется **заново**, не вырезается из `tension`/`macro_implication` (то же ограничение, что уже привело к несогласованным падежам при попытке генерировать вопросы на лету из сырого текста — см. `docs/ANALYSIS-preset-question-grammar.md`)
- **Называть сущность — нормально, если сигнал не претендует на роль победителя tension кластера** (обычный случай для `complication`/`background`; уточнено 2026-07-31, было прямое внутреннее противоречие с соседним пунктом ниже — см. заметку). Осторожность нужна только для сигналов, которые МОГУТ стать победителем (`trigger`/`resolution` с реальным шансом на max `contradicts`) — там называние сущности отвлекает матчинг от кластера, который вот-вот покажет именно этот сигнал
- **Обязательная проверка — но ПОСЛЕ мержа и автосинка, не до записи (см. Шаг 8, обновлено 2026-07-30).** Матчинг сравнивает с агрегированной tension кластера в `data/synthesis_cache.json`, которая пересчитывается только после мержа — проверка до этого момента тестирует против ещё неактуальных данных. `cluster_label` не обязан соответствовать именно кластеру ЭТОГО сигнала — честный матч на СУЩНОСТЬ (`findMatchingEntity()`) тоже засчитывается, если сигнал называет значимую сущность и сам сигнал не стал «победителем» tension кластера (обычный случай). Пропуск проверки вообще — тот же класс риска, что уже трижды материализовался в этой сессии (столкновение с сущностью, падежное несовпадение, пересечение слов между кластерами), только здесь на масштабе каждого нового сигнала, не разового курируемого пула
- **НЕ покрывается Immutability Policy** (AD-7) — в отличие от `tension`/`macro_implication`, это чисто UI-подсказка, не часть нарративного синтеза. Можно редактировать или убирать задним числом, если позже найдётся проблема — не нужно создавать новый сигнал ради исправления одного вопроса

> **Заметка (2026-07-31):** до этой правки два соседних пункта одного и того же поля прямо противоречили друг другу — «не называет сущность» (2026-07-28, без исключений) и «честный матч на сущность... нормально и даже лучше» (2026-07-30, для не-победителей). На практике проверено эмпирически (`STR-2026-0724-003`, разбор в сессии с Claude): вопрос БЕЗ имени сущности («Ниже какого порога доходности возможна реструктуризация долга?») даёт матч на кластер, но показывает tension ЧУЖОГО сигнала-победителя (`STR-2026-0720-001`, про дилюцию акций — не про BTC Floor ARR, о котором реально спросили). Вопрос С именем сущности («...у Strategy?») честно показывает профиль самой сущности — ближе к теме вопроса, хоть и не показывает именно этот сигнал (структурное ограничение анализатора, не решается формулировкой). Это и есть ровно та ситуация, которую предвидел пункт от 2026-07-30 — второй пункт был прав, первый устарел и не обновлён вовремя.

**`macro_implication`** — ответить на вопрос «что это меняет для BTC структурно».
Не пересказ события — вывод об изменении в системе.

| ❌ Плохо | ✅ Хорошо |
|---------|---------|
| «Franklin подала заявку на ETF» | «Пассивный дивидендный поток как источник BTC-спроса — новая категория не зависящая от настроений рынка» |
| «Metaplanet купила Siiibo» | «BTC-казначейство эволюционирует от пассивного баланса к операционному движку: коллатерал → лицензия → продукты → комиссионный доход» |

**`narrative_role`** — выбрать одну роль:

| Роль | Критерий | Расшифровка для сводки |
|------|---------|------------------------|
| `trigger` | Первый сигнал нового кластера или резкий перелом | открывает цепочку |
| `complication` | Добавляет противоречие в существующий нарратив | усложняет нарратив |
| `resolution` | Закрывает `tension` предыдущих сигналов | закрывает противоречие |
| `background` | Структурный контекст без острого события | структурный контекст |

### Шаг 7 — Проверка

Сигнал готов к оформлению только если:

- `tension` сформулирован по формуле (не описание факта)
- **Обязательно (2026-07-27):** прогнать `python3 scripts/check_new_tension.py "<черновик tension>"` — даёт немедленный PASS/FAIL по длине и балансу сторон, не полагаясь на память о числовом ориентире. Введено после того, как смоделировали дрейф на реальных данных: превышение длины tension накапливалось не линейно, а взрывными пачками (напр. 4 сигнала подряд 2 июля 2026), и три недели держалось на плато 16–18,5% от общего числа сигналов, ни разу не снизившись само по себе — агрегатный неблокирующий монитор (`tests/golden/test_tension_benchmarks.py`) годится для отслеживания системного сдвига, но не предотвращает создание очередного нарушителя в моменте
- **Если заполняется `preset_question`** — обязательно прогнать через `localAnalyzeSignal()` и убедиться, что он матчится именно на кластер ЭТОГО сигнала (см. правило поля выше) — не пропускать проверку по аналогии с уже написанными вопросами, каждый новый нужно проверять отдельно
- `macro_implication` отвечает на «что меняется структурно» (не пересказ)
- `narrative_role` выбрана и обоснована
- `links` — все три поля проверены по критериям шага 5
- `alternatives_considered` содержит ≥1 содержательную альтернативу с причиной отклонения
- `alternative_scenario` заполнен, если уверенность не высокая (иначе — обоснованно пропущен, не забыт)

Если что-то не выполнено — вернуться к соответствующему шагу.

### Шаг 8 — Оформление

**Присвоить `id`:**
Формат `PREFIX-YYYY-MMDD-NNN`. Перед записью открыть `signals.json` и найти все существующие `id` с той же датой и тем же префиксом. `NNN` — следующий порядковый номер. Если `STR-2026-0626-001` уже есть → `STR-2026-0626-002`.

**Чеклист перед записью:**
- JSON валиден — нет незакрытых скобок, нет лишних запятых
- `id` уникален в `signals.json`
- `catLabel` соответствует `cat` по канонической таблице справочника
- Все обязательные поля заполнены (прошёл шаг 7)
- `ENTITIES.json` обновлён, если в сигнале участвуют значимые сущности (см. «База артефактов»)
- **LLM Wiki Пара 1 (v8.17, тестируется органически на новых сигналах, не автоматизировано):** если сигнал — о компании, у которой уже есть запись в `REVENUE_ENGINES.json` (проверить по `entity_id`), проверить: подтверждает ли сигнал текущий `trend`/`trend_evidence`, или меняет его — обновить запись тем же коммитом, если да. Не для каждого сигнала о компании — только если он содержательно относится именно к доходному механизму (дивиденды, выпуск инструментов, обслуживание долга), не к любому упоминанию компании
- **Golden Dataset для contradiction detector (v8.29, `docs/PLAN-open-initiatives.md` Часть 2, «Пример A»):** если на Шаге 5 пара сигнал↔кандидат дала однозначное, показательное решение (явный confirms или contradicts, не пограничный случай) — добавить как новую пару в `tests/golden/fixtures/contradiction_pairs_extended.json` тем же коммитом. Не для каждого сигнала — только когда решение уже принято Шагом 5 и не требует отдельного анализа
- Если Шаг 4 завёл **новый** `cluster` — добавлена строка в `DIGEST_CLUSTER_LABELS` (`index.html`); для существующего кластера этот пункт не применим
- `signals.json` обновлён; `python3 scripts/build_signals_md.py` запущен, `SIGNALS.md` обновлён тем же коммитом (не редактировать `SIGNALS.md` напрямую — см. правило выше)
- `python3 scripts/build_signals_index.py` запущен, `data/signals_index.json` обновлён тем же коммитом (та же логика, что для `SIGNALS.md` — производный файл, не редактируется руками)
- Коммит использует префикс `signal:` (не `feat:`/`fix:`), формат —
  см. [`CONTRIBUTING.md`](CONTRIBUTING.md#commit-message-convention)
- **`preset_question` — обязательный follow-up ПОСЛЕ мержа и синка, не в исходной записи (2026-07-30).** Матчинг сравнивает вопрос с агрегированной tension всего кластера (`data/synthesis_cache.json`), которая пересчитывается только после мержа — до этого момента любая проверка "потемну". Стандартная процедура для каждого нового сигнала:
  1. Смержить PR сигнала, подождать автосинк (см. «Нарративный синтез» выше — не мержить sync-PR вручную)
  2. Подобрать 1-2 кандидата вопроса и проверить каждый через `localAnalyzeSignal()` против уже пересчитанного `data/synthesis_cache.json`
  3. Если сигнал НЕ стал «победителем» tension своего кластера (обычный случай) — кандидат может честно матчиться на СУЩНОСТЬ (`findMatchingEntity()`), если сигнал называет значимую сущность, а не на кластер: это нормально и даже лучше — ответ будет по существу о сигнале/сущности, не о чужом «победившем» сигнале кластера
  4. Записать `preset_question` отдельным коммитом (`feat:`, не `signal:` — это не новый сигнал)

`index.html` не трогать — кроме одной строки в `DIGEST_CLUSTER_LABELS` при новом кластере (см. выше и чеклист).

## Нарративный синтез (кратко)

Полная документация → [ALGORITHM.md](docs/ALGORITHM.md). Карточка нарратива строится из полей сигналов — алгоритм не генерирует текст, он **выбирает лучшее** из написанного.

**Score сигнала** (формула `_score_signal`, ALGORITHM.md):

| Компонент | Значения |
|-----------|----------|
| Свежесть | ≤7 дней = **+3** · ≤30 дней = **+1** · старше = 0 |
| `weight` | `onchain` = **+4** · `primary` = **+3** · `market` = **+2** · `media` = **+1** |
| `narrative_role` | `trigger` = **+4** · `complication` = **+3** · `resolution` = **+2** · `background` = 0 |
| `links.contradicts` | **+5 за каждый id** в списке (без верхнего предела) |

> `tension` в score не участвует — он определяет текст карточки, не ранжирование.

**Что определяет текст карточки** (уточнено 2026-07-31 — см. заметку ниже, было рассинхронено с кодом):

```
tension          → главный крючок (золотая полоса). Приоритет: свежий сигнал с
                    ролью resolution закрывает tension БЕЗУСЛОВНО, независимо от
                    числа contradicts (Priority 1, _select_tension_source());
                    если resolution нет — сигнал с max links.contradicts (Priority 2)
narrative        → основной текст (partA) — ВСЕГДА из anchor_trigger.macro_implication
                    (первый по рангу trigger; если триггеров нет — первый сигнал по
                    рангу вообще). Не зависит от resolution.
key_takeaway     → отдельный, третий приоритет: anchor_complication → anchor_trigger →
                    anchor_resolution → top_weight_signal (первый, чей macro_implication
                    ещё не использован в tension/narrative)
narrative_role   → приоритет при выборе anchor-сигнала
```

**Правило управления tension кластера:**
Блок «Главные нарративы» показывает tension победителя. Два способа его сменить:
1. **Самый прямой:** добавить новый сигнал с ролью `resolution`, закрывающий tension по критерию Шага 6 — он безусловно побеждает независимо от числа `contradicts` у текущего лидера (Priority 1 выше). Часто проще и быстрее второго пути — не нужно «перегонять» контрадикты.
2. Добавить **новый** сигнал с сильным `tension` и бо́льшим `links.contradicts`, чем у текущего лидера — **только через честный тест Шага 5**, накрутка запрещена.

В обоих случаях: не редактировать `tension`/`macro_implication` уже существующего сигнала задним числом (Immutability Policy, `docs/NIES.md` AD-7: immutable после первого синтеза, в котором сигнал использован).

> **Заметка (2026-07-31):** до этой правки строка выше ошибочно объединяла `narrative` и `key_takeaway` в один приоритет («из resolution → trigger → top_weight»), не совпадавший ни с кодом, ни с полным `docs/ALGORITHM.md` (который сам был верен) — `narrative` на самом деле не зависит от `resolution` вообще, а `key_takeaway` использует другой порядок (`complication → trigger → resolution → top_weight`). Отдельно, путь через `resolution` (Priority 1, безусловно побеждающий) не был упомянут явно — только про max `contradicts`. Найдено при стратегическом аудите системы на масштабирование (сессия с Claude) — тот же класс дрейфа «документация против кода», что уже ловили трижды (AD-6), только здесь ещё не был пойман. Нет отдельного автоматического теста-стража на этот конкретный абзац (в отличие от таблицы кластеров, `test_claude_md_cluster_table_matches_ontology_json`) — текстовое описание алгоритма в прозе плохо поддаётся такой проверке; полагаться на внимательность при следующих правках `docs/ALGORITHM.md`/`scripts/synthesizer.py` синхронно с этим абзацем.

**Автосинк после мержа сигнала — ждать, не мержить вручную (2026-07-30).** После мержа PR с сигналом CI сам создаёт `bot/sync-synthesis-*` PR с пересчитанным `data/synthesis_cache.json` и сам ставит его в очередь на автомерж (`gh pr merge --auto`, `allow_auto_merge: true` на уровне репозитория). Обычно завершается в течение ~1–2 минут после того, как на самом sync-PR позеленеет `Validate and Test`.

```
✗ Искать sync-PR вручную и мержить его самому — не нужно, это уже
  автоматизировано; ручное вмешательство в это окно может создать
  гонку состояний с логикой закрытия устаревших sync-PR (см. комментарии
  в .github/workflows/deploy.yml)
✓ Подождать ~1-2 минуты, затем проверить data/synthesis_cache.json
  напрямую (raw.githubusercontent.com или git pull) — если он уже
  отражает новый сигнал, синк завершился сам
```

Проверить фактический статус смерженного sync-PR нужно через **отдельный GET на сам PR** (`/pulls/{number}`), не через список (`/pulls?state=closed`) — список не всегда отдаёт поле `merged` надёжно.

## База артефактов (ENTITIES.json)

При разборе каждого сигнала Claude выявляет значимые сущности и обновляет `ENTITIES.json`.

### Типы артефактов

| type | Примеры |
|------|---------|
| `l2` | Stacks, Rootstock, Citrea, Botanix |
| `protocol` | Lightning, Stratum V2, wBTC |
| `corporate` | Strategy, GoMining, Bitplanet, Nakamoto |
| `fund` | Polychain Capital, BlackRock, Fidelity |
| `infrastructure` | Antalpha, Bitmain, Chainlink, DMND |
| `exchange` | Coinbase, OKX, Arkham |

### Схема объекта

```json
{
  "id": "stacks",
  "name": "Stacks",
  "type": "l2",
  "status": "active",
  "summary": "Одна строка — суть сущности",
  "profile": {
    "what": "Что делает",
    "metrics": ["ключевая метрика", "..."],
    "links_to": ["bitcoin", "ethereum"],
    "notable": "Ключевой факт или отличие"
  },
  "signal_refs": ["INF-2026-0609-001"],
  "last_updated": "YYYY-MM-DD"
}
```

### Правила обновления

- **Новая сущность** → создать объект и добавить в `ENTITIES.json`
- **Известная сущность** → обновить `profile` свежими данными + добавить `signal_ref` + обновить `last_updated`
- **Критерий значимости** → сущность попадает в базу если упоминается в контексте сигнала как участник события, а не просто как сравнение
- `status`: `active` / `closed` / `pending`

## HOLDERS_DATA — правило верификации (data/holders.js)

`data/holders.js` — снэпшоты распределения BTC по 6 категориям (`individuals`, `lost_satoshi`, `governments`, `companies`, `etfs`, `not_mined`) на конкретные даты. Используется таблицей «Структура владения» **и** панелью «Ключевые тренды» на сайте.

**Правило:** если в ходе обработки сигнала (Шаг 2 — Исследование) встречается свежая цифра по сумме владения любой из этих категорий — она проверяется и, если данные обновились, добавляется новый снэпшот (или уточняется существующий, если снэпшот той же даты уже есть). Это не про сам сигнал — сигнал обрабатывается по обычному алгоритму Шагов 1–8; снэпшот HOLDERS_DATA — побочный, но обязательный апдейт, если попавшиеся цифры релевантны.

**«Ключевые тренды» (2026-07-13) — computed, не хранится отдельно.** Панель `computeHolderTrend()` строит текст (первая точка → пик → последняя точка, или простой рост, если пика нет) напрямую из `HOLDERS_DATA.snapshots` при каждой отрисовке — отдельно поддерживать её не нужно: любое обновление снэпшота по правилу выше автоматически отражается и здесь. До этой даты панель была захардкоженным массивом текста, молча разошедшимся с реальностью после обновления снэпшота до Jul 2026 (ссылалась на Oct 2024).

### Методология категорий

- **`individuals` — residual**, не независимо измеренная величина: `21 000 000 − (lost_satoshi + governments + companies + etfs + not_mined)`. Так устроены все предыдущие снэпшоты (сумма категорий равна 21,000,000 по построению) — новый снэпшот обязан сохранять эту же логику, иначе датасет станет внутренне противоречивым.
- **`not_mined`** — считается напрямую из текущего блока эмиссии, не требует стороннего источника для основного значения; для перепроверки годятся live-трекеры circulating supply (Newhedge, MacroMicro, Blockchain.com) — если 2+ независимых сходятся в пределах погрешности, использовать без дополнительных оговорок.
- **`lost_satoshi`, `governments`, `companies`, `etfs`** — оценочные категории, разные агрегаторы (Arkham, River Financial, BitcoinTreasuries.net, Glassnode, Chainalysis, MEXC/KuCoin-обзоры) дают несовпадающие цифры, иногда на разные даты внутри одного месяца.
- **Сверка с `facts.json`** — при обработке каждого нового сигнала с category-релевантной цифрой сверять и с агрегатными фактами (`top100_public_companies`, `etf_exchanges` и т.п.), не только с прямыми category-сигналами. Не всякий связанный факт означает коррекцию — например, `top100_public_companies` (подмножество) согласуется с текущим `companies` без изменений, а `etf_exchanges` (ETF+биржи вместе) методологически не взаимозаменяем с чистым `etfs`. Фиксировать вывод сверки в комментарии к снэпшоту в любом случае — согласуется или нет.

### Обязательные оговорки при добавлении/обновлении снэпшота

- Если источники по одной категории расходятся — фиксировать оба значения в комментарии к записи (не выбирать молча), указывать почему выбран именно этот источник (специализация трекера важнее общего агрегатора)
- Указывать дату каждого использованного источника отдельно — снэпшот часто составной (разные категории с разных дат), это не единый пруф на одну дату
- После пересчёта `individuals` (residual) — проверять, что сумма всех категорий даёт ровно 21,000,000; если нет — арифметика неверна, искать ошибку до записи

### Приоритетные источники по категориям (для будущих обновлений)

| Категория | Предпочтительный источник |
|-----------|---------------------------|
| Companies | BitcoinTreasuries.net (уже основной источник проекта — предпочесть его общим агрегаторам типа MEXC/KuCoin, если данные доступны) |
| ETFs | BitcoinTreasuries.net, Farside Investors |
| Governments | Arkham Intelligence (специализированный трекер, предпочесть общим обзорам) |
| Individuals/whales | BitInfoCharts rich list, Glassnode |
| Lost/Satoshi | Chainalysis (оригинальная методология), Glassnode |

## FACTS — машиночитаемые факты (целевая архитектура, v8.2)

**Проблема, которую решает этот раздел:** BDKS и NIES уже декларируют принцип Single Source of Truth — «корпус сигналов — единственная база записей; производные базы ссылаются, не копируют» (NIES, S12: «направление синхронизации неизменно — производное приводится к источнику»). На практике этот принцип массово нарушался: `index.html` и `ENTITIES.json.profile.metrics` годами копировали числа текстом вместо ссылки на сигнал-источник. Конкретный подтверждённый случай: `signals.json.meta.strategy_btc_reserve` (847 363, обновлено вручную 25 июня) разошёлся с реальным фактом из сигнала STR-2026-0706-001 (843 775, 5 июля) — расхождение никто не поймал бы, если бы его не заметили руками.

**Решение:** опциональное поле `facts` в схеме сигнала (см. «Сигнал: схема объекта» выше) — структурированное дополнение к свободнотекстовому `data`, не замена. `scripts/build_facts.py` сканирует все сигналы, для каждого `key` выбирает запись с максимальным `as_of` (не порядок в файле, не дата сигнала) и пишет `data/facts.json`. Этот файл — производный, регенерируется автоматически (`.github/workflows/build-facts.yml` при каждом изменении `signals.json`), **никогда не редактируется руками** — тот же принцип, что уже действует для `SIGNALS.md`.

### Когда заполнять `facts[]`

Если сигнал содержит числовой факт по сущности или категории, которая уже отображается (или в перспективе может отображаться) где-то на сайте — заполнить `facts[]` тем же коммитом, что и сам сигнал. Не обязательно для каждого числа в `data` — только для тех, что имеют смысл как отслеживаемая метрика с историей обновлений (холдинги сущности, доля категории владения и т.п.), не для одноразовых контекстных цифр.

### Формат ключа

`entity_id.metric` — `entity_id` переиспользует `id` из `ENTITIES.json` там, где сущность там существует (например `strategy`); для агрегатных категорий без отдельной сущности (`top100_public_companies`, `governments`, `etf_exchanges` и т.п.) — любой стабильный snake_case идентификатор. Оба сегмента — snake_case, схема (`schemas/signal/v1.json`) валидирует формат через regex.

### Что НЕ проходит через этот механизм

- **Детерминированные/протокольные числа** (эмиссия по номеру блока, халвинг-математика) — вычисляются напрямую, сигнал не нужен
- **Live-fetch данные** (hashrate, цена, объём торгов) — уже есть рабочий пайплайн (mempool.space, CoinGecko via `data/volume.json`), не нужно тащить через сигналы

### Использование на сайте

`index.html` вызывает `fetchFacts()` при инициализации → `window.FACTS[key]` → `{value, unit, as_of, signal_id}`. Приоритет разрешения значения там, где раньше было захардкожено или бралось из `meta`: **facts.json → signals.json.meta (устаревающий вручную) → константа-fallback**.

**Универсальный механизм для HTML:** любой элемент с `data-fact-key="entity_id.metric"` автоматически подхватывает значение через `applyFactsToDOM()` при каждом `fetchFacts()` — не нужно писать код на каждое новое место миграции, достаточно проставить атрибут. Оборачивать только само число в разметке, текст вокруг не трогать (`data-fact-format="k"` — сокращённый вид, например «844K»).

**Синхронизация TREASURY_HOLDERS.json:** `scripts/build_facts.py` также сверяет поле `btc` у 100 публичных компаний-держателей с фактами по явному маппингу имён (`TREASURY_NAME_TO_FACT_KEY` — намеренно explicit, не fuzzy-match, чтобы не смэтчить не ту компанию). Расхождение логируется (`::warning::`) и правится — обнаружено и исправлено сразу 3 случая (Strategy, Strive, OranjeBTC) при первом прогоне на реальных данных.

### Защита от расхождения (урок AD-6 — тест-страж сразу, не постфактум)

`tests/unit/test_facts.py` — проверяет: (1) внутри одного сигнала нет дублирующихся `facts[].key`; (2) `resolve_facts()` корректно выбирает запись с максимальным `as_of` независимо от порядка сигналов в файле; (3) `sync_treasury_holders()` правит только замапленные записи и не трогает остальные. `tests/unit/test_contract_schemas.py` автоматически валидирует `facts[]` каждого сигнала против JSON Schema.

**Фаза 5 — сторожевой аудит против повторного дрейфа.** Миграция (Фазы 1–4) была процедурной — числа искались вручную. Процедура без механизма проверки в этом проекте исторически не держится (AD-6). `scripts/check_stale_facts.py` берёт **полную историю** значений каждого отслеживаемого ключа (`build_facts.superseded_values()` — не только текущее по `as_of`, а все когда-либо встреченные) и ищет любое из устаревших значений голым текстом в `index.html`/`TREASURY_HOLDERS.json` — вне `data-fact-key` (там placeholder безопасен, перезаписывается JS) и вне JS-констант fallback (`const NAME = число;` — намеренно ниже `facts.json` в приоритете, не дублирующее отображение). Оформлен как pytest-тест (`test_no_forgotten_stale_fact_copies_in_index_html`), не отдельный CI-шаг — попадает в основной прогон автоматически, не требует отдельного подключения в workflow, которое можно забыть. Проверен на подставленном кейсе (`test_check_stale_facts_catches_injected_stale_copy`) — детектор действительно ловит, не просто молча проходит на чистом репозитории.

При первом реальном прогоне сразу нашёл забытое место (`mstr-live-btc` — обновлялось отдельным JS-механизмом напрямую по `id`, не через `data-fact-key`) — унифицировано на единую конвенцию вместо добавления исключения в сторож.

### Текущий охват

Сущности с fact-трекингом (`entity_id.btc_holdings`; `strategy` дополнительно даёт `usd_reserve`): `strategy`, `metaplanet`, `twenty_one_capital`, `mara_holdings`, `bstr`, `strive`, `oranjebtc`, `el_salvador`, `spacex`. Плюс агрегатные категории без отдельной сущности в ENTITIES.json: `top100_public_companies`, `etf_exchanges`.

Числа-счётчики намеренно не фиксируются в прозе (было «12 ключей, 9 сущностей» — протухало почти при каждом новом facts-сигнале, см. v8.9): список сам себе счётчик, его длину видно, не считая отдельно.

## SITE_MAP — карта структуры сайта (v8.5)

**Проблема:** за сессию несколько раз находки о дублировании/устаревании контента обнаруживались случайно, не системно (график эмиссии дублировал 3 места, панель уезжала не в тот кластер, футер не обновлялся из-за неправильного триггера вкладки) — потому что не было машиночитаемой карты структуры сайта, только сам `index.html` на 7000+ строк. Та же природа проблемы, что решал FACTS для данных — здесь решается для структуры.

**`data/site_map.json`** — единственный источник истины по структуре: на каждую панель/раздел — кластер, вкладка, тип контента (`kind`), происхождение данных (`source`), ключевые слова для поиска. Заполняется вручную (авто-извлечение из разнородной разметки ненадёжно), но **сверяется тестом в обе стороны**:

- `test_every_manifest_title_exists_in_html` — ловит переименованную/удалённую панель, если манифест не обновили
- `test_every_html_panel_title_is_in_manifest` — ловит новую панель, которую забыли занести в манифест

Записи с `"dynamic": true` (например «Дайджест сигналов по кластерам» — целиком JS-рендерится, нет статичного literal-текста) исключены из первой проверки — по построению нечего сверять.

### Значения `source`

| Значение | Смысл |
|----------|-------|
| `live` | живой fetch при каждой загрузке (mempool.space, Yahoo Finance) |
| `facts` | из механизма FACTS (`data/facts.json`) или синхронизируемых JSON (`TREASURY_HOLDERS.json`, `data/holders.js`) |
| `static` | статичные данные, обновляются только вручную |
| `signals` | нарративный синтез из корпуса сигналов, не число |
| `none` | методология/описание, живых данных нет |
| `tool` | интерактивный инструмент (AI-анализатор), не витрина данных |

### UI — интерактивное дерево

Кнопка 🔍 в шапке → полноэкранный оверлей: поиск по названию/ключевым словам/вкладке, дерево кластер→вкладка→запись с цветным бейджем `source`, клик — переход на вкладку + скролл к панели. Переход ищет панель **по точному тексту заголовка** (`.panel-title`/`.acc-label`/`.instrument-ticker`), не по `id` — расставлять уникальные id на полсотни существующих панелей ради одной этой функции было бы избыточным риском для минимальной пользы; текстовый поиск работает надёжно и не требует трогать разметку панелей вообще.

### При добавлении новой панели на сайт

Добавить запись в `data/site_map.json` (title — точное совпадение с `panel-title`/`acc-label` в HTML, cluster/tab — куда встроена, source — по таблице выше, keywords — по смыслу) тем же коммитом. Тест поймает несоответствие, если забыть — но лучше не полагаться только на это.

## LLM Wiki — связывание не только сигналов (план, v8.37)

> **Открытые пункты (Пары 1, 3, 4, 5)** → [docs/PLAN-open-initiatives.md](docs/PLAN-open-initiatives.md) Часть 1 — читать перед тем, как продолжать эту работу в новой сессии. **Полная история решений и отклонённых пар (7)** → [archive/PLAN-llm-wiki-cross-linking.md](archive/PLAN-llm-wiki-cross-linking.md) (закрыто, см. архив).

**Идея (2026-07-25):** Фаза 1 ADR-018 связывает сигналы между собой. Тот же принцип — расширить на связи между **любыми** блоками сайта (сущности, доходные движки, теория, функции протокола, холдеры), чтобы Bitcoin Intel был не набором отдельных вкладок, а связной базой знаний.

**Дисциплина та же, что уже действует для сигналов** (см. обсуждение в чате): не «связать всё сразу» — каждая пара блоков получает **свой** честный тест перед автоматизацией, реализуется по одной, оценивается на реальных данных, прежде чем переходить к следующей. Тот же принцип поэтапности, что ADR-011/ADR-018.

### Систематический аудит-чекпоинт для Пар 8/9 (v8.36, 2026-08-03)

**Проблема, найденная в сессии 2026-08-03:** до этой находки связи Пар 8/9 появлялись только когда одна и та же сессия случайно работала над обоими узлами одновременно (Coinkite получил `theory_refs` и `function_refs` не потому что это единственная релевантная сущность, а потому что RNG-баг Coldcard и разбор мультисига пришлись на одну сессию). Между **уже существующими**, ничем не связанными узлами (напр. Lightning Labs и панель «Как работает маршрутизация» — оба существовали месяцами) не было НИКАКОГО механизма, который бы вообще заметил потенциальную связь. Ручная проверка нашла 6 честных кандидатов за два прохода (Runes↔OP_RETURN, Tangem↔Multisig, $DOG Mode↔Governance, Foundry↔Governance, Breez↔Lightning-routing, BitGo↔Multisig — второй проход явно расширил скан на типы corporate/fund/exchange, изначально отфильтрованные без проверки) — подтверждает, что пропуски были реальны, не гипотетичны.

**Испробовано и отклонено — TF-IDF не работает на этом масштабе.** По аналогии с ADR-018 (TF-IDF для сигналов) была сделана попытка `scripts/find_missing_wiki_links.py` — та же схема (уни+биграммы, косинусное сходство). На реальных данных подтверждённая вручную пара Lightning Labs↔«Проблема ликвидности» дала скор 0.032, а заведомо нерелевантная пара («Research» из governance) — 0.046 выше. Для $DOG Mode топ-скор вообще пришёлся на постороннюю панель («Математика взлома» парольной фразы, 0.029), честная пара governance/Enforcement — 0.017. **Причина** — корпус (29 сущностей × 30 пунктов теории × 6 функций) слишком мал, тексты слишком коротки для статистически осмысленного TF-IDF (в отличие от signals.json, где 100+ содержательных документов делают IDF нетривиальным). Скрипт удалён, не оставлен как «слабый, но рабочий» — он не просто слабый, он **систематически ранжирует шум выше настоящих связей**, оставлять его как источник кандидатов значило бы хуже, чем ничего не иметь.

**Рабочий механизм — обязательная процедурная проверка, не скрипт:**

1. **При создании новой сущности** → перед завершением записи явно сверить её `summary`/`profile.what` против **всех** топиков `THEORY_TOPICS.json` и **всех** записей `BITCOIN_FUNCTIONS.json` (не только тех, что случайно всплыли в текущем материале) — тем же честным тестом, что и для сигналов: «добавляет ли понимание одного узла реальный, конкретный контекст другому — не просто тематическая близость». Без ограничения по типу сущности — первый проход 2026-08-03 ограничивался типами `l2`/`protocol`/`infrastructure` и из-за этого пропустил честного кандидата (`bitgo`, type `exchange`, прямо называет себя «пионером мультиподписных кошельков»); второй проход нашёл его именно расширив скан на все типы.
2. **При создании нового топика/пункта THEORY_TOPICS.json или записи BITCOIN_FUNCTIONS.json** → симметрично, сверить против всех сущностей без ограничения по типу.
3. **Периодический полный проход** (бэкстоп на случай пропуска пунктов 1-2, или если два старых узла стали релевантны друг другу задним числом из-за третьего, более нового) — на каждое **+1.0** (мажорное) обновление этого файла, тем же счётчиком, что уже отслеживает версионный дрейф (см. «Версионное напоминание» ниже) — напомнить о необходимости полного прохода по всем текущим сущностям (всех типов) против топиков/функций.

Двусторонняя кликабельность (не только данные) обязательна для новых связей Пар 8/9 — `theory_refs`/`function_refs` на сущности **и** соответствующий `crosslink` (`type:'entity'`) на топике/функции, оба направления проверяются реальным рендером (`renderFunctionCard`/`renderAccItem`/`showEntityPopup` через Node-харнесс), не только валидностью JSON.
