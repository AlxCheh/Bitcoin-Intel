# Разбор: несклад в рандомных вопросах кластеров

> **Дата:** 2026-07-28
> **Статус:** анализ для решения пользователем — код ещё не менялся под этот разбор.

---

## 1. Реальные примеры несклада (со скриншота)

| Что показано | Что не так |
|---|---|
| «Что с баланса до 7700 BTC?» | «с» требует творительного падежа («с балансом»), а «баланса» — родительный. Слово взято из фразы «рост **баланса**» (родительный там уместен), но вырвано в контекст, где нужен другой падеж |
| «Что с на каждые $1.57 млн BTC, делая?» | Начинается с предлога «на» — грамматически невозможное начало фразы после «Что с» |
| «Что с млн BTC несмотря на 5.58 млн?» | Начинается с «млн» — это сокращение единицы измерения, не самостоятельное слово, не может открывать фразу |

## 2. Корневая причина — не баг, а предел самого подхода

Текущий механизм (`pickRandomWordWindow` + `generateClusterPresetQuestion`) берёт **случайное окно из 4–6 слов** внутри первой части реальной тензии кластера и подставляет его после «Что с …?». У него уже есть фильтр читаемости (`JUNK_WORD_START`) — список из 16 предлогов/союзов, на которые окно не должно начинаться или заканчиваться.

Проблема глубже списка:

1. **Список неполный.** «на» отсутствует в `JUNK_WORD_START` — тривиально дополняется, но это latает симптом, не причину.
2. **Сокращения единиц измерения** («млн», «млрд», «трлн», «тыс.») тоже не самостоятельные слова, но это отдельная категория, не предлог — нужен отдельный список.
3. **Главное — согласование падежей вообще не проверяется.** Конструкция «Что с ⟨X⟩?» грамматически требует, чтобы X начиналось в **творительном падеже**. Слово в источнике находится в ЛЮБОМ падеже, в зависимости от его роли в исходном предложении — «баланса» (родительный, после «рост») это грамматически корректное слово, просто не в том падеже, который нужен после «с». **Никакой список стоп-слов на входе/выходе окна эту проблему не решает** — можно исключить все предлоги и все сокращения единиц измерения, и всё равно получить «Что с баланса…?», потому что «баланса» — совершенно нормальное, не служебное слово, просто не в той форме.

## 3. Почему нельзя починить это списками — честная оценка

Задача «проверить, что случайно выбранное русское слово стоит в творительном падеже» — это морфологический анализ. В браузере (JS, без библиотек морфологии типа pymorphy2) у нас нет доступа к такому анализу. Можно:

- Написать эвристику по окончаниям слов (творительный падеж существительных часто оканчивается на -ом/-ем/-ой/-ей/-ами/-ями) — но это **приблизительно**, ловит не все случаи, и даст новый класс ложных срабатываний (пропустит корректные слова с нестандартным окончанием, пропустит неправильные с окончанием, похожим на творительный случайно)
- Список стоп-слов и стоп-начал — сужает пространство плохих случаев, но принципиально не может гарантировать грамматическую корректность, потому что падеж — свойство КАЖДОГO существительного/прилагательного в окне, не только первого слова

**Вывод: рандомная генерация "окна слов из реального текста" не может надёжно давать грамматически верный русский без полноценного морфологического анализатора, которого у нас нет.**

## 4. Рекомендуемое решение — расширенный курируемый пул + случайный выбор

Возврат к принципу, который уже работал раньше в этой сессии (единственный вопрос на кластер), но с **несколькими проверенными вариантами на кластер** вместо одного — рандомность становится **выбором из готового, вручную написанного и грамматически корректного пула**, а не **генерацией на лету** из сырого текста.

### Правила курирования (для каждого кластера)

1. **4–6 готовых вопросов на кластер**, каждый:
   - Грамматически полное, естественное русское предложение-вопрос
   - Использует слова, реально встречающиеся в `tension`/`narrative` этого кластера (не обязательно точную словоформу — вопрос пишется вручную с нуля, не вырезается из текста) — но должен **реально совпадать** через `localAnalyzeSignal()`, проверено скриптом, не на глаз
   - Не содержит имя сущности, которое приоритетно матчится через `findMatchingEntity()` (тот же урок, что уже был с «Strategy» — см. `docs/CHANGELOG.md`)
2. **Обязательная проверка каждого вопроса** — тот же принцип, что уже применяется:
   ```
   const r = localAnalyzeSignal(вопрос);
   r.matched && r.cluster_label === expectedLabel  // должно быть true
   ```
3. **Случайный выбор одного из пула** при каждом рендере `generatePresetSignals()` — рандомность сохраняется, но из проверенного множества, не из непроверяемого пространства всех возможных окон слов
4. Сущности — уже работающий рандомный выбор из топ-8 по покрытию сигналами (эта часть работает корректно, падежей не касается — «Сколько BTC у ⟨Имя⟩?» не зависит от склонения имени собственного)

### Чего это НЕ решает и что теряется

- **Вопросы не будут обновляться сами по себе** при появлении новых сигналов — придётся вручную добавлять новые варианты в пул, когда появляется значимо новый сигнал в кластере (аналогично тому, как мы уже поддерживаем `CLUSTER_PRESET_QUESTIONS`)
- Это откат от «генерируется само из базы» к «курируется человеком, база только подсказывает слова» — честно признаю, это менее автоматизировано, чем текущий (сломанный) подход, но единственный вариант, который **гарантированно** не выдаёт несклад

## 5. Альтернатива, если хотите оставить генерацию на лету

Можно попытаться доработать эвристику (расширить `JUNK_WORD_START`, добавить список сокращений единиц измерения, добавить примитивную проверку окончаний на творительный падеж) — но я должен быть честен: **это снизит частоту несклада, не устранит его полностью**. При достаточном числе прогонов (сайт открывают много раз) рано или поздно вылезет новый неучтённый случай — так уже случилось дважды подряд (акронимы, затем падежи).

## 6. Мой рекомендуемый выбор

**Вариант из раздела 4** — расширенный курируемый пул. Он медленнее в поддержке, но единственный, что даёт твёрдую гарантию грамотности, которую явно ожидаете вы как владелец проекта.
