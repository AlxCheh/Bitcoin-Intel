## Флейк Node-харнесса — наблюдён один раз, причина НЕ подтверждена (2026-08-15)

**Что видел:** `tests/unit/test_functions_entities_crosslinks.py::TestEntityPopupFunctionRefs::test_function_ref_renders_clickable_badge_with_looked_up_name` упал один раз в полном прогоне. Тот прогон занял **55 секунд вместо обычных ~25** — то есть шёл под заметной нагрузкой.

**Что проверено сразу:** тест изолированно — проходит; два последующих полных прогона — 629 passed; CI на том же коммите — зелёный. Воспроизвести не удалось.

**Гипотеза (именно гипотеза, не диагноз):** `run_node_js()` (`tests/conftest.py`) запускает Node-подпроцесс с `timeout=10`. Под нагрузкой подпроцесс мог не уложиться, и `subprocess.TimeoutExpired` дал бы падение, не связанное с содержанием теста.

**Почему не исправлено:** трейсбек упущен — команды были сцеплены через `&&`, и вывод прокрутился до того, как я его прочитал. Поднимать таймаут «на всякий случай» без подтверждения означало бы лечить симптом ненаблюдавшейся болезни: если причина другая (гонка при записи временного файла, конкуренция за Node, что-то в самом тесте), правка таймаута замаскирует её, а не устранит.

**Что делать, если повторится — по порядку:**
1. Прогнать **без сцепления команд**, сохранить полный трейсбек: `python -m pytest tests/unit/test_functions_entities_crosslinks.py -vv --tb=long > /tmp/trace.txt 2>&1`
2. Посмотреть, `TimeoutExpired` это или падение ассерта. Это развилка: первое — инфраструктура, второе — реальная логика.
3. Если `TimeoutExpired` — прежде чем менять `timeout=10`, замерить, сколько подпроцесс реально занимает под нагрузкой. Значение подбирать по замеру, не наугад.
4. Если ассерт — искать зависимость от порядка тестов (`pytest -p no:randomly` / запуск только соседних файлов), это уже не флейк, а скрытая связь между тестами.

**Класс риска.** Пока флейк единичный — он дешевле, чем поспешная правка. Но если станет регулярным, он опаснее обычного падения: команда привыкает к красному прогону и перестаёт читать, что именно упало. Этот же класс проблемы уже стоил проекту дорого — CRLF-false-positive обесценивал каждый локальный прогон, пока его не устранили (`.gitattributes`, 2026-08-15), а до того тест precision молча скипался много дней (B1 ARR v3).

## Настоящий рейтинг адресов сети требует платного API (2026-08-16)

**Что произошло.** Панель «Топ-100 богатейших адресов» опиралась на Blockchair (`api.blockchair.com/bitcoin/addresses`) — единственный найденный бесплатный источник ранжированного списка. Источник закрылся: HTTP 430, «Your IP address is temporary blacklisted… Please apply for an API key». 430 приходит и с раннеров GitHub Actions, и с локальной машины при 1 запросе в сутки — то есть блокировка не про нагрузку проекта, бесплатный тариф без ключа для этих диапазонов IP просто закрыт.

**Что сделано взамен.** Источник заменён на `blockchain.info/balance` (проверен фактически, один batch-запрос на все адреса). Но он умеет только «баланс по известному адресу», поэтому выборка сузилась до курируемого `data/known_addresses.json` (38 адресов), а панель переименована в «Крупнейшие известные адреса» — прежнее название стало бы враньём.

**Чего теперь нет.** Ранжирования по всей сети. Адрес, не попавший в курируемый список, в панели не появится, каким бы крупным ни был.

**Условия возврата к настоящему рейтингу — любое из:**
1. **API-ключ Blockchair** — писать на info@blockchair.com, вероятно платно. Потребует секрет в GitHub Actions и станет первой платной внешней зависимостью проекта; решение владельца, не техническое.
2. **Другой источник с ранжированием.** Проверены и отброшены 2026-08-16: `blockchain.info/charts/top-100-addresses` отдаёт HTML (был JSON когда-то), `blockstream.info`/`mempool.space` рейтинга не предоставляют вовсе — только баланс по адресу. `bitinfocharts.com` отдаёт HTML-страницу с рейтингом, но это скрейпинг: хрупко к вёрстке и требует проверки ToS.
3. **Расширение курируемого списка.** Не даёт рейтинга сети, но сужает разрыв. Отдельная курационная работа: адрес нужно атрибутировать (кому принадлежит), а не просто добавить строку.

**Не делать наивно:** не возвращать название «Топ-100», пока источник не даёт рейтинга по сети. Название переобещало и до поломки — панель называлась «Топ-100», а показывала 10 записей.

**Само собой восстановилось** к 14 августа — токен где-то был обновлён вне этой сессии.

**Что проверить, если повторится:** `SYNTHESIS_BOT_TOKEN` в GitHub Settings → Secrets and variables → Actions — не fine-grained PAT ли это с истёкшим сроком (в отличие от classic PAT они истекают по умолчанию через 90 дней, если явно не выставлено «No expiration»). Если да — обновить и рассмотреть более долгий срок или GitHub App вместо PAT (не истекает вовсе).

## Дубль даты в data/volume.json — найден и исправлен тем же днём (2026-08-16)

**Что нашли.** Проверяя, не оставили ли падения `Update BTC Volume Data` (см. выше) дыр в данных — дыр не нашлось (окно перезаписывается целиком каждый раз), но нашлось другое: `history` содержал **31 запись на 30 уникальных дат** — две записи на `2026-08-16` с разными значениями объёма (10.4 и 9.35 млрд USD).

**Причина.** `scripts/fetch_volume.py` предполагал, что CoinGecko `market_chart` с `interval=daily` отдаёт ровно одну точку в день. На практике последняя точка не всегда выровнена на UTC-полночь — два разных timestamp схлопывались в одну календарную дату через `strftime("%Y-%m-%d")`.

**Исправлено.** `build_volume_payload()` дедуплицирует по дате, оставляя последнюю по времени точку при дубле (более свежий снимок за форминг-день). Добавлен guard на случай вырожденного края (все точки схлопнулись в одну дату). 8 новых тестов на фикстуре, реконструирующей реальный дубль, плюс регрессия на сам закоммиченный файл. `data/volume.json` перегенерирован.

## `findMatchingEntity()` не матчит многословные имена сущностей (2026-08-22)

**Что нашли.** При подборе `preset_question` для `STR-2026-0811-001` (новая сущность `trump_media`) вопрос «Сколько BTC держит Trump Media?» не матчился вообще — ни на сущность, ни на кластер, хотя сущность только что создана и содержательна.

**Причина.** `findMatchingEntity()` сравнивает каждый ЗНАЧИМЫЙ ТОКЕН вопроса (одно слово) с ПОЛНОЙ строкой кандидата (`e.id` или очищенное от скобок `e.name`) через Левенштейна, с допуском `Math.abs(token.length - cand.length) > 3` — отсекает пару до сравнения. Для однословных сущностей (`foundry`, `antpool`, `strive`) токен вопроса и кандидат совпадают по длине — работает. Для многословных (`trump_media` / «Trump Media & Technology Group Corp.») ни один отдельный токен вопроса не близок по длине к длинной строке-кандидату целиком — совпадения не будет никогда, вне зависимости от формулировки вопроса.

**Проверено не только на новой сущности** — тем же Node-харнессом (`localAnalyzeSignal`/`findMatchingEntity`, что и для `preset_question`) воспроизведено на уже существующих `mara_holdings` («MARA Holdings») и `twenty_one_capital` («Twenty One Capital») — оба тоже не матчатся на прямой вопрос про них. Значит это не баг конкретно новой записи — системный пробел, существовавший и раньше, просто не был замечен, пока не понадобился честный тест конкретно для многословной сущности.

**Почему ничего не сделано сразу.** Правка `findMatchingEntity()` (например: сравнивать конкатенацию значимых токенов вопроса со всей строкой кандидата, а не токен-к-строке) — изменение самой логики сайта (`js/app-main.js`), не оформление одного сигнала; по правилу «Изменения index.html» из CLAUDE.md требует отдельного рассмотрения через `docs/spec-pilot.md`, не входит в рамки записи сигнала.

**Практическое следствие прямо сейчас.** `STR-2026-0811-001` записан БЕЗ `preset_question` — не забыто, осознанно: сигнал не стал победителем tension кластера (значит вопрос должен матчиться на сущность), а честный матч на сущность структурно недостижим для многословного имени. Форсировать вопрос, который упадёт в непредсказуемый cluster-fallback (или вовсе в «нет совпадений»), было бы нечестной практикой ровно того типа, для защиты от которой существует обязательная проверка `localAnalyzeSignal()` на этом шаге.

**Что нужно, если решим действовать.** Одна из: (а) в `findMatchingEntity()` сравнивать не «токен vs кандидат», а «весь ввод vs кандидат» через token-set сравнение (например, доля значимых токенов кандидата, найденных где-то во вводе, с толерантностью к опечаткам на уровне отдельных токенов); (б) отдельный, более дешёвый путь матчинга по алиасам/сокращениям (`aliases` в схеме сущности) в дополнение к `id`/`name`. Оба варианта требуют юнит-тестов на существующих многословных сущностях (`mara_holdings`, `twenty_one_capital`, `trump_media`, `samourai_wallet` — готовый регрессионный набор из четырёх случаев, последний подтверждён при проверке `INF-2021-0804-001`) и реального Node-рендер-теста, не только оформления.
