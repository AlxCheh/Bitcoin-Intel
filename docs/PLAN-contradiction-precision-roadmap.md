# PLAN: Contradiction Detector Precision — рабочий план с известным ограничением

> **Начато:** 2026-07-31 · **Обновлено:** 2026-07-31
> **Источник:** обсуждение в чате — прямое продолжение находки при расширении Golden Dataset (ADR-012, заметка 2026-07-31): честная precision на 116 парах — 54.3%, ниже enforced-порога 60% на исходных 73.
> **Связанные документы:** `docs/ADR-009-contradiction-scoring.md` (формула, заметка 2026-07-31 про shared-subject-conflict), `docs/ADR-012-contradiction-precision-target.md` (порог 60%/85%, путь к N=150), `docs/ADR-018-signal-similarity-candidate-expansion.md` (тот же принцип «кандидат ≠ решение» для соседней задачи)

**Принцип документа:** ограничение precision не скрывается и не считается разовым багом для починки — это известное, измеренное свойство lexicon-based детектора, с которым работаем осознанно. План отвечает на три вопроса: (1) как это влияет на процесс уже сегодня, (2) как это видно постоянно, (3) как и когда пересматривается решение.

---

## 0. Роль детектора в процессе — почему это не гонка за 85%

`suggest_contradictions()`/`semantic_inverse_score()` — **только генерация кандидатов**, не решение. Каждый кандидат в любом случае проходит три честных теста Шага 5 человеком, прежде чем попасть в `links.contradicts` (тот же принцип, что уже действует для TF-IDF-кандидатов из ADR-018). Финальный гейт — всегда человек, не score.

Следствие: детектор с precision 54% и гипотетический с 85% дают **одинаково надёжный конечный результат** в `signals.json` — разница только в том, сколько нерелевантных кандидатов аналитик отсеивает по пути. Это меняет приоритет: разрыв 54%→85% важен для эффективности разбора (меньше шума в `suggest_contradictions()`), но не является вопросом корректности данных — заводить его как критический некорректно.

---

## 1. Операционная политика — Шаг 5 уже был правильным гейтом

Ничего не меняется в процедуре — фиксируется явно то, что уже верно:
- Кандидат из детектора — предложение, не готовое решение, независимо от score.
- Три честных теста Шага 5 (confirms / contradicts / context_chain) обязательны для КАЖДОГО кандидата, включая High-score — высокий score не освобождает от проверки.

---

## 2. Расширение Golden Dataset — гибрид, не единая процедура

Развилка обсуждения: расширять датасет постоянно (по одному сигналу) или батчами. Ответ — оба, для разных случаев, различающихся по стоимости:

### Пример A — кандидат уже проверен Шагом 5 (дёшево → постоянно, в чеклист Шага 8)

Если на Шаге 5 сигнал уже был сопоставлен с кандидатом из того же кластера/`find_similar_signals.py` и решение (confirms/contradicts/не связаны) уже принято — это секундный вопрос «эта пара достаточно однозначна для golden dataset?», не новый анализ. Так появились 14 из 43 пар при расширении 73→116 (harvest уже принятых связей из `data/relationships.json`).

**Пункт в чеклист Шага 8** (при обработке сигнала, если уместно): если пара сигнал↔кандидат из Шага 5 — однозначный, показательный случай (явный confirms/contradicts, не пограничный) — добавить как новую пару в `tests/golden/fixtures/contradiction_pairs_extended.json` тем же коммитом. Не обязательно для каждого сигнала — только когда решение уже принято и однозначно.

### Пример B — кандидата не было вообще (дорого → периодические батчи)

В маленьких/однонаправленных кластерах (пример: `quantum_security` на момент находки) Шагу 5 физически не с чем сравнивать — сравнение нужно придумать проактивно, провести суждение с нуля. Так появились 29 из 43 пар сегодня. Это отдельная аналитическая сессия, не побочный продукт обработки одного сигнала.

**Процедура:** периодически (не по расписанию — когда видно, что несколько кластеров слабо покрыты, см. секцию 4) — сессия по образцу сегодняшней: обзор непокрытых/слабо покрытых кластеров → проактивный подбор пар → честный тест на каждую → добавление батчем.

| **A. Узкие независимые сигналы** | По мере находки новых пропущенных/ложных паттернов (как shared-subject-conflict сегодня) — новый независимый сигнал через `max()`, не правка существующих весов (`polarity_score`, `_inverse_pair_score`). Каждая попытка тестируется на **обоих** датасетах: (a) ноль регресса на blocking (73), (b) измеримый прирост на extended (116) — методология «до/после на фиксированном срезе», не тренд headline-числа во времени (extended сам усложняется по мере роста через Пример B — тренд может стоять на месте при честном прогрессе). | **C. Явное решение по потолку lexicon-подхода** | Открытое решение из трёх вариантов (см. секцию 5) | Срабатывает по триггеру секции 4, не по календарю |

## 4. Триггеры пересмотра — явные, не «как-нибудь потом»

- **N=3 подряд отклонённых независимых попытки** (Этап A), каждая честно доведена до теста на обоих датасетах — без единого попадания → сигнал переходить к явному разговору по Этапу C. Не через календарное время (3-4 сессии — слишком расплывчато и легко проигнорировать), а через 3 доведённых до конца попытки, сколько бы времени они ни заняли. Прецедент из сегодняшней сессии: 2 отклонённых (negation-aware polarity, точечная фраза) + 1 успешная (shared-subject-conflict) — счётчик не достиг 3, продолжаем Этап A.
- **Extended-датасет упал ниже sanity-порога 45%** — уже enforced тестом (`test_precision_on_extended_golden_pairs_tracking_only`), немедленное расследование при первом же красном прогоне.
- **N достиг 150** (ADR-012) — обязательный честный пересчёт, тем же протоколом, что применён сегодня к переходу 73→116 (не предполагать результат до факта).

## 5. Этап C — решение по умолчанию, не три равноправные опции

При срабатывании триггера секции 4 варианты:
- **(a) Продолжать узкие сигналы до 85%.** Не подтверждено данными: 3 попытки сегодня дали 1 успешную (+0.9 п.п.) — экстраполяция на разрыв в 30 п.п. предполагает ~30 таких находок подряд, при том что shared-subject был, вероятно, самым очевидным случаем. Не основной путь по умолчанию.
- **(b) Семантический слой (TF-IDF-фича по прецеденту ADR-018, либо эмбеддинги/NLI — Фаза 3 ADR-018).** Отличие от ADR-018: там кандидат-генерация — ошибка дешева (более широкий список для человека). Здесь уверенный, но неверный score вводит в заблуждение именно в момент, когда аналитик должен проверить сам — а объяснимость (`(score, term)` вместо голого числа) — то, что делает Шаг 5 быстрым уже сегодня (пример: shared-subject-conflict называет конкретную фразу и глаголы, NLI дал бы только число). Реальная цена без ясной выгоды при текущей роли инструмента.
- **(c) Осознанно принять потолок ~60-65% для lexicon-подхода, формально снизить aspirational-цель в ADR-012.** **Default-исход**, не равноправная опция — см. секцию 0: раз финальный гейт всегда человек (Шаг 5), разница между 60% и 85% автоматической precision даёт меньше практической пользы, чем кажется на бумаге, а (b) добавляет реальную цену (потеря объяснимости) без ясной выгоды для этой конкретной роли инструмента.

**Пересмотр самого default-исхода (c):** только если роль детектора в процессе изменится — например, решение автоматически принимать `contradicts` без review Шага 5 (тогда цена ошибки вырастает, и разговор про (b) становится оправданным заново). До этого — (c) остаётся отправной точкой при срабатывании триггера, не (a)/(b).

## 6. Видимость

`scripts/quality_report.py` → `check_contradiction_precision()` — печатает precision на blocking (73) и extended (116) в человекочитаемом отчёте и в `--format json`, рядом с уже существующей секцией Calibration (тот же паттерн, ADR-011). Не заводит отдельный персистентный лог трендов — история и так видна через `git log` по golden-фикстурам и коммитам с `fix:`/ADR-заметками (третий подобный механизм за сессию был бы избыточен, см. `data/synthesis_history_count.json` и `data/facts.json` — двух уже достаточно для этого класса задач).
