## Ловушки: что стоило времени в этой сессии

### 1. Коммит напрямую в `main` из инерции

Несколько раз за сессию — особенно **после долгих не-git активностей** (написание дизайн-дока, брейнсторм, исследование через WebSearch) — я коммитил прямо в `main`, забыв создать ветку, хотя весь остальной рабочий процесс сессии строго шёл через ветку → PR → авто-мердж после CI. Каждый раз приходилось откатывать через `git branch -f`/detached checkout, не через `reset --hard` (пользователь один раз явно отклонил `reset --hard`, даже безопасный).

**Правило:** проверять `git branch --show-current` перед первым `git add`/`git commit` в новом смысловом блоке работы, не полагаться на память о том, что «мы же на ветке».

### 2. Дизайн-док может содержать технически неверные утверждения, даже когда макет уже утверждён пользователем

Визуально утверждённый макет (карточки, порядок блоков) не проверяет технические УТВЕРЖДЕНИЯ дизайн-дока о том, ГДЕ именно в коде что-то лежит и что чем переиспользуется. Дважды за один дизайн-док (реорганизация ОБЗОРА) пришлось чинить: (1) нарративы рендерит `renderDashboard()`, не `renderDashStatus()` — угадал не глядя; (2) «график цены уже дублируется на МЕТРИКИ» — оказалось неправдой при grep, элемент существовал в одном экземпляре, только на ОБЗОРЕ.

**Правило:** любое конкретное техническое утверждение в дизайн-доке («уже дублируется», «эта функция уже делает Х») — grep-проверить перед переносом в implementation plan, не полагаться на память о структуре кода даже в рамках одной сессии.

### 3. Тесты, извлекающие ВЕСЬ файл целиком (не через `extract_js_function`), ломаются от несвязанного нового кода в том же файле

`tests/unit/test_scroll_handler_throttling.py` грузил весь `js/app-early.js` в мок с одним `window.addEventListener`-перехватчиком, рассчитанным на единственный `scroll`-слушатель в файле. Добавление второго независимого `scroll`-слушателя (кнопка «к содержанию») в тот же файл сломало тест — мок перехватил не тот обработчик.

**Правило:** при добавлении нового module-level кода (особенно `addEventListener`/`requestAnimationFrame`-подписок) в `js/app-early.js`/`js/app-main.js` — искать тесты, которые грузят файл целиком через `.read_text()` + `src.replace(...)`, не через `extract_js_function()`, и проверять их допущения о «единственности» до, не после красного прогона.

### 4. `behavior:'smooth'` не анимируется в этом автоматизированном браузере (claude-in-chrome/CDP)

Потрачено время на диагностику мнимого бага скролла кнопки «к содержанию» — оказалось, `scrollIntoView({behavior:'smooth'})` не анимируется даже при прямом нативном вызове через `Runtime.evaluate` в этой среде (не специфично для кода сайта). Мгновенный вариант (`{block:'start'}` без `behavior:'smooth'`) сработал сразу и подтвердил, что логика верна.

**Правило:** при проверке scroll-функциональности через браузерную автоматизацию — если `behavior:'smooth'` визуально «не работает» на скриншотах, сначала проверить `behavior` без `smooth`, прежде чем считать это багом кода. `{behavior:'smooth'}` — уже устоявшаяся конвенция сайта, менять её ради среды автоматизации не нужно.

### 5. Навигация браузерной автоматизацией по сайту — не полагаться на текст ссылки буквально

При первой проверке эссе Сэйлора клик по тексту «В ТЕОРИЮ →» привёл не туда — элемент с таким текстом оказался не связан с реальной вкладкой-навигацией (`siteMapGoTo(...)` на конкретную панель, не общий переход). Прямой вызов `showTab('theory', null)` через JS оказался надёжнее клика по похожему на нужный, но семантически другому элементу.

**Правило:** при проверке через браузерную автоматизацию — для переключения вкладок использовать `showTab(id, null)` напрямую через `javascript_tool`, не искать «похожую» кликабельную ссылку на странице.

### 6. Скилл `spec-pilot`, упомянутый в CLAUDE.md, — общий мета-скилл, не специфичный алгоритм сборки для этого сайта

Название и описание в таблице CLAUDE.md («Алгоритм сборки для задач с index.html») наводят на мысль, что это специфичная для проекта инструкция. На деле это универсальный скилл «интервью → спека → саб-агенты → проверка» (лид-магнит к внешнему видео), не содержащий ничего специфичного для Bitcoin Intel. Полезно знать заранее — не тратить время на поиск специфичных для сайта указаний внутри него.

## Процедурные напоминания

- **Автосинк после мержа сигнала** — ждать, не мержить sync-PR вручную (`docs/CI_RUNBOOK.md`).
- **Локальный `gh pr merge` в этом окружении регулярно падает на шаге синхронизации `main`** (`Not possible to fast-forward`), уже после успешного squash на GitHub. Проверять `gh pr view <N> --json state` прежде чем повторять. При `mergeStateStatus: BEHIND` — `git fetch origin main && git merge origin/main` на ветке PR, дождаться нового зелёного CI, повторить мерж (за эту сессию понадобилось минимум 4 раза, стабильно воспроизводится, не считать аномалией).
- **PR не мержить без явного «смержи»/«мерджи» от пользователя** — установившийся за все сессии паттерн, включая AEO/редизайн-работу следующей сессии.
- **Workflow-файлы могут отставать от кода, который они запускают.** После добавления `scripts/prerender_home.py` в `deploy.yml` (P0 этого файла) — перепроверить, что весь job `synthesize` по-прежнему логически согласован (порядок шагов, что коммитится).
