**Условия возврата к настоящему рейтингу сети** зафиксированы в `docs/BACKLOG.md` («Настоящий рейтинг адресов сети требует платного API») — три варианта, каждый требует решения владельца (API-ключ Blockchair, вероятно платно) или отдельной курационной работы (расширение списка известных адресов).

**Решение владельца:** цель — «читают ли вообще» (простой счётчик посещений), без cookies/PII. Сервис — **Cloudflare Web Analytics** (beacon-скрипт, не требует проксирования DNS через Cloudflare, работает поверх GitHub Pages как есть).

**Сделано:** `<script type="module" data-cf-beacon>` добавлен в `<head>` `index.html` сразу после `<title>`. Токен сайта получен владельцем в дашборде Cloudflare (Analytics & Logs → Web Analytics → alxcheh.github.io).

**Не покрыто этим решением** (см. таблицу целей в исходной постановке P0 ниже) — «какие кластеры читают» и «работает ли нарратив» остаются открытыми, если возникнет интерес к более глубокому сигналу: потребуют событий на уровне вкладок/карточек, не покрываются базовым pageview-счётчиком Cloudflare.

**Проверка:** данные в дашборде Cloudflare появляются с задержкой (обычно в течение суток после первых визитов) — саму работу счётчика на живом сайте стоит подтвердить в следующей сессии, не в момент вставки скрипта.

## P0 (исходная постановка) — Слабость 5: нет сигнала об аудитории

**Почему первым.** Это единственное направление из исходного разбора слабостей, к которому вообще не притрагивались, и единственное, которое про **читателя**, а не про внутреннюю корректность. Прошлая сессия девять PR подряд улучшала модель данных — то есть воспроизводила ровно тот перекос, который эта слабость и описывает: вся рефлексия проекта про корректность внутренней модели, ни одной метрики про людей.

**Что известно (проверено grep'ом, не по памяти):** инфраструктуры нет вообще. Ни `analytics`, ни `gtag`, ни `plausible`, ни `visitor`, ни `pageview` — ноль совпадений по `index.html`, `js/*.js`, всем `docs/*.md`. Вкладка «АНАЛИТИКА» на сайте — про метрики сети Bitcoin, не про читателей.

**Ограничение, определяющее решение:** сайт — статичный GitHub Pages, бэкенда нет. Это исключает серверную аналитику и делает выбор нетривиальным.

**Первый шаг — не код, а решение.** Прежде чем что-либо ставить, нужен ответ владельца на вопрос, который нельзя вывести из репозитория: **зачем** нужен сигнал об аудитории. Варианты ведут к разным решениям:

| Цель | Что из неё следует |
|---|---|
| «Читают ли вообще» | достаточно счётчика посещений, любой privacy-first сервис |
| «Какие кластеры читают» | нужны события на уровне вкладок/карточек |
| «Работает ли нарратив» | нужна глубина/время на карточке — сложнее и спорнее |
| «Не нужно, достаточно признать пробел» | документационное закрытие, как AD-8 |

**Обязательная оговорка при обсуждении.** Проект тщательно относится к честности данных; сторонняя аналитика — это внешняя зависимость и вопрос приватности читателя. Нужно проговорить явно, а не ставить скрипт по умолчанию. Вариант «признать пробел документально и не собирать ничего» — легитимный исход, не поражение.

## P3 — AD-10: только когда появятся данные

**Не начинать без основания.** Единый `STALE_THRESHOLD = 30` против требования BAMS Р3 различать скорость устаревания по категориям («рыночные быстро, инфраструктурные медленно»).

**Почему отложен:** категорийные пороги требуют назначить числа («инфраструктура 90, рынок 14»), а данных нет. Это та же «фиктивная точность», которую ADR-011 уже отклонила для коэффициентов confidence. Повторить её для порогов свежести было бы прямой непоследовательностью.

**Что дало бы основание:** наблюдаемая скорость изменения метрик по категориям — эмпирика, а не умозрение. Пока такой оценки нет, пункт не трогать.

**Blast radius, если всё же браться:** `_freshness()` → score → ранжирование → выбор anchor → tension карточки. MAJOR по ADDENDUM §25.3 с переутверждением golden-ожиданий.

**Целевое поведение уже зафиксировано:** кейс `target-infrastructure-not-stale-under-category-threshold` в эталонном наборе Р9 — он проходит уже сейчас и показывает, что `layer2_programmability` поднимется до «Высокой».

## Ловушки: что стоило прошлой сессии времени

Каждая проверена на реальных данных, не гипотетическая.

### 1. Прогонять формулу на реальном корпусе ДО написания кода

Сработало **четыре раза**, каждый раз меняя решение. Каждый раз наивный вариант прошёл бы CI и выглядел правдоподобно:

| Наивный вариант | Что показал прогон |
|---|---|
| `links.contradicts` → «неразрешённое противоречие» Р9 | **инвертировал** ранжирование: кластеры с 22/16/16 прямыми сигналами → «низкая», односигнальные → «средняя» |
| `disputed_facts` у любого сигнала кластера | наказывал крупные кластеры за объём: 1 спор из 28 сигналов топил весь кластер |
| строгий «только anchor» для `alternative_scenario` | потерял бы `layer2_programmability` целиком |
| детектор сущностей v1 | 833 кандидата почти сплошного шума |

### 2. Коллизии терминов — искать до реализации

Дважды одно слово означало разное, и оба раза долг был сформулирован так, будто значение одно:

- **`contradicts`**: тип 3 по BAMS Р7 (разнонаправленные процессы, **повышает** score) vs «неразрешённое противоречие» Р9 (тип 1, конфликт фактов, **понижает** уверенность)
- **«Golden Dataset»**: 6 реальных прецедентов BDKS Р13 (валидация методологии) vs 15 синтетических сигналов `tests/golden/` (детерминизм кода)

### 3. Локализация дефекта прежде маркера

Прошлая сессия едва не пометила `xfail` кейсы, где тестируемая функция была **исправна** — дефект (AD-10) находился выше по потоку, в вычислении входа. Маркер обвинил бы не тот компонент, а при закрытии долга `strict=True` дал бы `xpass` и потребовал трогать посторонний файл.

**Правило:** прежде чем помечать тест ожидаемо падающим — проверить, что падает именно тестируемый компонент.

### 4. `conftest.py` подменяет рабочую директорию

Autouse-фикстура `isolated_environment` делает `chdir(tmp_path)` для **каждого** теста и кладёт туда заглушки `signals.json` / `ENTITIES.json` с пустым списком. Тест, читающий файл репозитория по относительному пути, либо упадёт с невнятной ошибкой, либо — хуже — молча скипнется.

Прошлая сессия попала в эту ловушку сразу, несмотря на предупреждение в докстринге самого `conftest.py`. **Резолвить от `Path(__file__)`.**

### 5. Требование объяснять ожидание словами ловит расхождения

Поле `derivation` в эталонном наборе Р9 вводилось как защита от snapshot-теста. Побочно оно вскрыло **AD-10** — расхождение кода со спецификацией, которое не видел ни один тест на равенство и не заметил ни один аудит.

**Переносимый приём:** заставить себя вывести ожидаемое значение из спецификации, а не скопировать из вывода функции.

### 6. Последний прогон workflow — недостаточная проверка (найдена 2026-08-16)

`Update Top Addresses Data` не отработал успешно **ни разу за 22 дня** (создан 25 июля), при этом каждый отдельный прогон был виден в Actions как обычное красное пятно — не заметили, потому что смотрели на факт «упало сегодня», не на историю. Красный шедулер не блокирует PR и не эскалирует сам по себе.

Проверка «последний прогон каждого workflow зелёный» не отличает «работает» от «сломано с первого дня, никто не смотрел». Разница обнаружилась только при явном запросе разобраться — по инициативе пользователя, не автоматически.

**Правило:** при любой проверке состояния CI/workflow смотреть не последний прогон, а распределение исходов по последним ~10 — `gh run list --workflow "<name>" --limit 10 --json conclusion --jq '[.[].conclusion] | group_by(.) | map({conclusion: .[0], count: length})'`. Разовая аномалия (1 падение среди 9 успехов) не требует действия; кластер (3+ подряд) или систематика (0 успехов) — требует.

- **Локальный `gh pr merge`** в этом окружении регулярно падает на шаге синхронизации `main` (`Not possible to fast-forward`), **уже после успешного squash на GitHub**. Проверять `gh pr view <N> --json state` прежде чем повторять — мерж, скорее всего, прошёл. Отдельно возможен `BLOCKED`/`mergeStateStatus` из-за защиты ветки, требующей свежий прогон — `git fetch origin main && git merge origin/main` на ветке PR, дождаться нового зелёного CI, повторить мерж.
- **При конфликте слияния между двумя параллельными PR в один и тот же раздел документа** (например, `docs/BACKLOG.md`, куда за сессию 08-16 писали два независимых PR подряд) — обычно это две независимые записи одного списка, не взаимоисключающие правки. Разрешать сложением, не выбором одной стороны.
- **Workflow-файлы могут отставать от кода, который они запускают.** После смены источника данных в скрипте (как `fetch_top_addresses.py` 08-16) проверить сам `.github/workflows/*.yml` на устаревшие упоминания старого источника — в комментариях, тексте автокоммита, теле создаваемого PR. Тесты этого не ловят, они не читают YAML.
