# Устранение гонки автомерджа — дизайн

> Статус: **пересмотрен** (вариант A оказался недоступен на этапе
> реализации, принят вариант B) · **Дата:** 2026-09-13

## Проблема

`main` защищён `required_status_checks.strict: true` («ветка должна быть
актуальной перед мерджем») — это осознанное и правильное требование: без
него PR может смержиться по проверке, снятой со устаревшего снэпшота кода,
не отражающего то, с чем он реально сольётся (именно так возник инцидент
2026-09-13 с календарным дрейфом golden-фикстуры — тесты были зелёными
на старом коммите и оставались бы зелёными сколько угодно, если бы никто
не заметил).

Но ничего не обновляет ветку PR автоматически. Когда несколько PR с
включённым auto-merge оказываются готовы почти одновременно —
после простоя пайплайна (как сегодня: 6 зависших bot/sync-* PR
накопились за сутки) или просто потому что параллельно подходят
bot-синки + сигнал + dependabot — каждый мердж мгновенно делает
следующий в очереди `behind`, и тот зависает: ничего не запускает его
`update-branch`. Сегодня это пришлось разгребать вручную —
`gh api .../update-branch` в три подхода для #1287/#1288 и ещё раз для
#1234, каждый раз ожидая пересчёта CI.

## Цель

Устранить необходимость ручного `update-branch` для PR любого
происхождения (bot/sync-*, signal/*, dependabot, ручные fix/feat) —
единым механизмом, не завязанным на тип PR.

## Не цели

- Не менять требование `required_status_checks.strict` — оно корректно
  и не является источником проблемы (см. «Проблема» выше).
- Не менять политику ревью (`required_approving_review_count: 0`
  остаётся как есть).
- Не трогать логику закрытия устаревших sync-PR в bot-workflow'ах
  (`gh pr close "$old_pr" --delete-branch`) — она решает другую задачу
  (не плодить дубликаты одного и того же bot-синка) и не конфликтует
  с итоговым решением.

## Обновление 2026-09-13 — вариант A отклонён при попытке реализации

Изначально выбранный вариант A (нативный GitHub Merge Queue) прошёл
Task 1 внедрения (триггер `merge_group` в `deploy.yml`, смержен,
PR #1291), но **Task 2 (включение самой очереди) провалился** —
подтверждено прямым вызовом API, не предположением:

```
POST /repos/AlxCheh/Bitcoin-Intel/rulesets
→ 422 {"errors":["Invalid rule 'merge_queue': "]}
```

Контрольный тест (та же нагрузка, `enforcement: "evaluate"` вместо
`"active"`) вернул явную причину того же класса:

```
"Enforcement evaluate option is not supported on this plan.
Please upgrade to Enterprise to enable it."
```

**Вывод:** репозиторий принадлежит личному аккаунту (`owner_type:
"User"`, не Organization) на бесплатном тарифе GitHub — часть
функциональности Repository Rulesets, включая правило `merge_queue`,
тарифицирована независимо от того, что сам репозиторий публичный.
Публичность репозитория (проверенная на этапе дизайна) была необходимым,
но не достаточным условием — тарифный план аккаунта проверен не был.
Это ошибка дизайна, не ошибка реализации: предпосылка «Merge Queue
бесплатен на публичных репозиториях» не была проверена против
фактического тарифа аккаунта, а доступная документация GitHub на
момент дизайна не дала прямого ответа на этот вопрос.

Апгрейд плана (GitHub Team) требует также переноса репозитория под
Organization (личные аккаунты на Team не переводятся) — решение о
биллинге/структуре владения, не техническое, принято не апгрейдить,
а перейти на вариант B.

## Рассмотренные варианты

**A. Нативный GitHub Merge Queue.** Отклонён на этапе реализации —
недоступен на текущем тарифе (см. «Обновление» выше). Архитектура
и обоснование, по которым он изначально был предпочтён, сохранены в
истории git этого файла — не переписываются задним числом.

**B. Свой workflow «автолечения» отставших PR (выбран).** См.
«Решение» ниже.

**C. Отключить `strict`.** Отклонён: возвращает тот же класс бага,
который вызвал сегодняшний инцидент — PR сможет смержиться по чекам,
снятым с устаревшего состояния кода.

## Решение — workflow «автолечения» отставших PR

Новый workflow, реагирующий на `push` в `main` — это и есть событие,
которое делает другие открытые PR `behind` (главный триггер гонки).
На каждый такой push: найти все открытые PR, у которых **одновременно**
включён auto-merge (`autoMergeRequest != null`) **и** `mergeStateStatus
== "BEHIND"`, и вызвать для каждого `update-branch` — то есть
автоматизировать ровно то ручное действие, которое выполнялось сегодня
через `gh api .../update-branch` три раунда подряд для #1287/#1288 и
ещё раз для #1234.

**Условие `autoMergeRequest != null`** — сознательное ограничение
охвата: чинит именно гонку непосещаемых мерджей (все зависшие вчера PR
её имели — все bot/sync-* включают auto-merge сразу при создании), не
трогает PR без auto-merge (как #1269/#1234 вчера) — там уже участвует
человек, который либо мержит вручную, либо сам решает включить
auto-merge, и тогда PR немедленно попадает под действие этого же
workflow на следующем push. Это и есть «единый механизм для всех типов
PR» — не по происхождению PR, а по факту готовности мержиться без
присмотра.

**Каскадный эффект:** мердж одного PR → новый push в `main` → workflow
срабатывает снова → подтягивает следующий отставший PR → тот мержится
(если его чек уже зелёный) → новый push → и так далее, пока очередь не
опустеет. Тот же результат, которого добивался вариант A через
нативную последовательную очередь, только через цепочку
push-триггеров вместо серверной очереди GitHub.

**Токен — `SYNTHESIS_BOT_TOKEN`, не `GITHUB_TOKEN`.** Тот же паттерн,
уже задокументированный в комментариях всех существующих
bot-workflow'ов (`update-bip110-signaling.yml` и аналогичные): push/API-
вызов, сделанный от имени штатного `GITHUB_TOKEN`, не порождает новый
workflow run на затронутом PR — «Validate and Test» не перезапустится
после `update-branch`, и PR зависнет уже по другой причине. Секрет уже
существует в репозитории и используется остальными bot-workflow'ами —
переиспользуется, не создаётся заново.

## Архитектура / необходимые изменения

### Новый файл: `.github/workflows/auto-update-behind-prs.yml`

```yaml
name: Auto-update behind PRs

on:
  push:
    branches: [main]

permissions:
  contents: read
  pull-requests: write

jobs:
  update-behind:
    name: Update branch for behind auto-merge PRs
    runs-on: ubuntu-latest
    steps:
      - name: Update branches
        env:
          GH_TOKEN: ${{ secrets.SYNTHESIS_BOT_TOKEN }}
          REPO: ${{ github.repository }}
        run: |
          gh pr list --repo "$REPO" --state open \
            --json number,autoMergeRequest,mergeStateStatus \
            -q '.[] | select(.autoMergeRequest != null and .mergeStateStatus == "BEHIND") | .number' \
          | while read -r pr; do
              echo "Обновляю ветку PR #$pr (behind + auto-merge)"
              gh api --method PUT "repos/$REPO/pulls/$pr/update-branch" || \
                echo "⚠ update-branch для #$pr не удался — не блокирует остальные PR"
            done
```

Точная реализация (обработка ошибок отдельных PR, логирование) —
детализируется на этапе плана реализации, не в дизайне.

## Риски / эджкейсы

- **Не мгновенная реакция.** Workflow реагирует на `push`, а
  `mergeStateStatus` GitHub пересчитывает не синхронно — может
  потребоваться секунд 5-10 после push, прежде чем `BEHIND` реально
  появится в ответе API. Решается небольшой паузой перед опросом или
  ретраем (детали — в плане реализации), не меняет архитектуру.
- **Нет истинной последовательности, в отличие от нативной очереди.**
  Если два PR становятся зелёными одновременно и оба ещё не `behind`
  на момент срабатывания workflow (гонка успела разрешиться сама),
  ничего страшного — они просто мержатся оба как обычно; workflow
  подстраховывает только случай, когда `behind` уже наступил.
- **Дополнительный workflow run на каждый push в `main`** — приемлемо
  по объёму (несколько запусков в день), но стоит иметь в виду при
  будущем аудите частоты CI.
- Логика закрытия устаревших sync-PR в bot-workflow'ах не
  затрагивается (см. «Не цели»).

## План проверки

1. Создать `.github/workflows/auto-update-behind-prs.yml`, смержить
   обычным путём.
2. Намеренно создать два PR с auto-merge почти одновременно (как
   вчера) — убедиться, что после мерджа первого workflow сам подтягивает
   второй без ручного `update-branch`.
3. Убедиться, что PR без auto-merge не трогаются этим workflow (создать
   один такой параллельно, убедиться что его `mergeStateStatus` не
   меняется от чужого push).

## Откат

Удалить файл `.github/workflows/auto-update-behind-prs.yml` — workflow
ни на что не влияет, кроме собственных вызовов `update-branch`, ничего
в branch protection не меняет.

## Наследие варианта A (не требует действий, справочно)

- `.github/workflows/deploy.yml` содержит триггер `merge_group:`,
  добавленный для варианта A (Task 1, PR #1291) — сейчас неактивен
  (никогда не срабатывает без включённой очереди), безвреден. Решено
  не откатывать — цена отдельного PR ради удаления неактивной строки
  выше пользы; при будущем переходе репозитория под Organization
  строка уже на месте для повторной попытки варианта A.
