# Merge Queue для устранения гонки автомерджа — дизайн

> Статус: предложен · **Дата:** 2026-09-13

## Проблема

`main` защищён `required_status_checks.strict: true` («ветка должна быть
актуальной перед мерджем») — это осознанное и правильное требование: без
него PR может смержиться по проверке, снятой со устаревшего снэпшота кода,
не отражающего то, с чем он реально сольётся (именно так возник инцидент
2026-09-13 с календарным дрейфом golden-фикстуры — тесты были зелёными
на старом коммите и оставались бы зелёными сколько угодно, если бы никто
не заметил).

Но ничего не обновляет ветку PR автоматически. Когда несколько PR с
включённым auto-merge оказываются готовы почти одновременно —
после простоя пайплайна (как сегодня: 6 зависших bot/sync-* PR
накопились за сутки) или просто потому что параллельно подходят
bot-синки + сигнал + dependabot — каждый мердж мгновенно делает
следующий в очереди `behind`, и тот зависает: ничего не запускает его
`update-branch`. Сегодня это пришлось разгребать вручную —
`gh api .../update-branch` в три подхода для #1287/#1288 и ещё раз для
#1234, каждый раз ожидая пересчёта CI.

## Цель

Устранить необходимость ручного `update-branch` для PR любого
происхождения (bot/sync-*, signal/*, dependabot, ручные fix/feat) —
единым механизмом, не завязанным на тип PR.

## Не цели

- Не менять требование `required_status_checks.strict` — оно корректно
  и не является источником проблемы (см. «Проблема» выше).
- Не менять политику ревью (`required_approving_review_count: 0`
  остаётся как есть).
- Не трогать логику закрытия устаревших sync-PR в bot-workflow'ах
  (`gh pr close "$old_pr" --delete-branch`) — она решает другую задачу
  (не плодить дубликаты одного и того же bot-синка) и не конфликтует
  с очередью.

## Рассмотренные варианты

**A. Нативный GitHub Merge Queue (выбран).** См. «Решение» ниже.

**B. Свой workflow «автолечения» отставших PR.** Триггер на `push` в
`main`, находит все открытые PR со статусом `mergeable_state == "behind"`
и сам вызывает `update-branch` — автоматизация того, что делалось
вручную сегодня. Отклонён: не устраняет гонку до конца — если два PR
становятся готовы одновременно, они всё равно могут гоняться друг за
другом несколько кругов подряд (ровно как произошло сегодня с
#1287/#1288, трижды подряд). Костыль поверх причины, не её устранение.

**C. Отключить `strict`.** Отклонён: возвращает тот же класс бага,
который вызвал сегодняшний инцидент — PR сможет смержиться по чекам,
снятым с устаревшего состояния кода.

## Решение — GitHub Merge Queue

Бесплатна на публичных репозиториях (`visibility: public` — подтверждено).
PR с зелёными обязательными чеками не мержится напрямую, а встаёт в
FIFO-очередь. GitHub сам собирает временный коммит «актуальный `main` +
голова очереди + этот PR», прогоняет обязательный чек именно на этой
комбинации и только тогда мержит — строго по одному, последовательно.
Следующий PR в очереди автоматически проверяется уже против только что
влитого предшественника. Ручной `update-branch` не нужен никогда —
для PR любого происхождения, что закрывает требование «единый механизм
для всех типов PR сразу» без специального кода под каждый тип.

Существующие bot-workflow'ы (`update-bip110-signaling.yml` и
аналогичные: `update-top-addresses.yml`, `update-volume.yml`,
`detect-pipeline-events.yml`, `quality-dashboard.yml`, `build-facts.yml`)
**не меняются**. Все они уже вызывают `gh pr merge --auto --squash
--delete-branch` сразу после создания PR — при включённой очереди
GitHub сам подставляет PR в неё вместо прямого мерджа, семантика
`--auto` совместима с очередью без изменений в скриптах.

## Архитектура / необходимые изменения

### 1. `.github/workflows/deploy.yml` — добавить триггер `merge_group`

Сейчас:

```yaml
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]
```

Единственный обязательный чек `main` — джоб `validate` («Validate and
Test») в этом файле. Он триггерится на `pull_request: branches: [main,
develop]` для ЛЮБОГО PR независимо от того, какой workflow его создал
(confirmed: `quality-dashboard.yml` и другие bot-workflow'ы не
определяют свой собственный одноимённый джоб — только упоминают
«Validate and Test» в комментариях как чужую зависимость). Это значит
правка нужна только в одном файле и покрывает все типы PR сразу.

Без `merge_group` джоб `validate` не запустится для PR, добавленного
в очередь — он зависнет там навсегда в ожидании чека, который никогда
не придёт (тот же класс проблемы, что уже задокументирован в
комментариях bot-workflow'ов про `GITHUB_TOKEN` vs `SYNTHESIS_BOT_TOKEN`,
но с другим триггером).

Джобы `synthesize` (строка 97) и `deploy` (строка 257) уже гейтятся
`if: github.ref == 'refs/heads/main' && github.event_name == 'push'` —
добавление `merge_group` их не заденет, они по-прежнему сработают
только на реальный push в `main` после фактического мерджа.

### 2. Branch protection `main` — включить Merge Queue

Метод мерджа в очереди — squash, тот же, что уже используют все
bot-workflow'ы (`--squash`) и ручные мерджи в этой сессии. Точный
API/UI-путь настройки (classic branch protection API vs. Repository
Rulesets — GitHub периодически переносит функциональность merge queue
между этими механизмами) — уточнить на этапе реализации через текущую
документацию GitHub API, не фиксируется здесь как окончательный.

Список обязательных чеков для очереди — тот же `["Validate and Test"]`,
что уже задан в `required_status_checks.contexts` (имя джоба не
меняется, переносить не нужно).

## Риски / эджкейсы

- `enforce_admins: true` уже включён на `main` — значит и ручные мерджи
  администратора (как сегодняшние `gh pr merge --squash` из этой сессии)
  тоже пойдут через очередь. Осознанный побочный эффект, не обход
  защиты — сохраняет ту же гарантию для всех, без исключений.
- PR, открытые на момент включения очереди, домерживаются по старому
  пути (прямой squash после ручного/авто разрешения `behind`) — очередь
  подхватывает только новые события auto-merge/enqueue после включения.
- Каждый мердж получает дополнительный прогон CI (~1 минута) — пересчёт
  на актуальном `main` перед фактическим слиянием. Приемлемо при текущей
  частоте синков (BIP-110 каждые 3 часа, volume/top-addresses/pipeline
  events ежедневно, сигналы и dependabot — по мере появления).
- Если два независимых bot-workflow создадут PR почти одновременно,
  оба всё равно последовательно пройдут очередь без ручного
  вмешательства — в отличие от сегодняшнего инцидента.

## План проверки

1. Включить `merge_group` в `deploy.yml`, замержить эту правку обычным
   путём (ещё без очереди).
2. Включить Merge Queue в branch protection `main`.
3. Дождаться или вручную запустить один bot-sync PR (`workflow_dispatch`
   на любой из `update-*`/`detect-*` workflow'ов) — убедиться, что PR
   встаёт в очередь, `merge_group` триггерит `validate`, PR мержится
   без ручного вмешательства.
4. Параллельно/следом провести один ручной PR (например, мелкий
   `docs:`-коммит) через тот же путь — убедиться, что очередь
   обрабатывает оба типа PR одинаково.
5. Намеренно создать два готовых к мерджу PR одновременно (как сегодня)
   — убедиться, что оба проходят очередь последовательно без ручных
   `update-branch`.

## Откат

Аддитивное изменение, откатывается в обе стороны независимо:
- Выключить «Require merge queue» в branch protection `main`.
- Убрать строку `merge_group:` из `.github/workflows/deploy.yml`
  (не обязательно немедленно — лишний триггер без активной очереди
  просто никогда не сработает).

## Открытые вопросы (для этапа реализации, не блокируют дизайн)

- Точный API/UI-путь включения Merge Queue на момент реализации
  (classic branch protection vs. Repository Rulesets).
- Нужно ли ограничивать очередь по числу параллельно собираемых
  групп (`merge_group_configuration.max_entries_to_build` в
  терминологии GitHub) — по умолчанию GitHub сам подбирает разумное
  значение, специальной необходимости менять не выявлено.
